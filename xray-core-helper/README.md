# Xray Core Helper

Привилегированный локальный control plane для Xray: анализ и настройка установленного Xray, типизированное редактирование JSONC, динамический список доменов и IPv4, geodata и безопасное применение native-шаблонов.

`xray-core-helperd` владеет обычными изменениями; CLI `xray-core-helper` и web-панель обращаются к нему через Unix socket. Исключение — самостоятельный режим установки/setup/recovery. Остановка helper не останавливает передачу трафика.

Установщик определяет бинарник, единственный конфиг и сервисную идентичность по эффективным настройкам `xray.service`. Каталог assets задаётся явным `XRAY_LOCATION_ASSET`. При неподдерживаемой конфигурации установка останавливается; отдельного параметра пути Xray в helper TOML нет.

Наличие конфига Xray не означает, что helper настроен. Первичная настройка запускается отдельно:

```bash
sudo /usr/local/bin/xray-core-helper setup
sudo /usr/local/bin/xray-core-helper setup --status
sudo /usr/local/bin/xray-core-helper health
sudo /usr/local/bin/xray-core-helper safe-apply status
```

`setup` — самостоятельный режим CLI без обращений к daemon: останавливает helper/web, берёт runtime lock и выполняет настройку в процессе. `setup --status` читает состояние через обычный socket; `setup --recover` восстанавливает состояние после прерванной настройки в том же автономном режиме. Диалог анализирует существующий конфиг или подготавливает начальный, готовит native-файлы сети; включение выполняется отдельным явным safe-apply TProxy-unit с подтверждением. Начальный outbound `proxy` выходит напрямую, пока оператор не задаст реальный прокси.

## Запуск сети

Подготовленная native-сеть работает независимо от helper. Постоянные правила
nftables не переключаются; отдельный drop-in Xray запускает policy routing
после старта и останавливает при stop/сбое. Ошибка routing делает запуск Xray
неуспешным. Нет отдельного enable, Python lifecycle или marker/lock, проверок
API/сокетов/mtime и вызовов helper в boot path.

Setup готовит файлы; явный safe-apply TProxy-unit устанавливает единственный
вспомогательный asset — Xray drop-in. Обновление factory-источника не подменяет
действующий drop-in; удаление helper сохраняет native-сеть. Диагностика и
ограничения — в [эксплуатации](../docs/OPERATIONS.md). Новый вариант требует
отдельной тестовой серверной приёмки.

## Динамические домены и IPv4

```bash
sudo /usr/local/bin/xray-core-helper proxy-domain add example.com
sudo /usr/local/bin/xray-core-helper proxy-domain add 192.0.2.1
sudo /usr/local/bin/xray-core-helper proxy-domain list
sudo /usr/local/bin/xray-core-helper proxy-domain delete example.com
sudo /usr/local/bin/xray-core-helper proxy-domain delete 192.0.2.1
```

Команда `proxy-domain`, endpoint `/v1/proxy-domains` и поле `domain` сохранены;
значение может быть доменом или IPv4, тип не выбирается вручную. Нормализацию,
классификацию и отклонение IPv6/CIDR/URL/некорректного IPv4 выполняет helper, а
не CLI. Список живёт в той же SQLite-хранилище `desired`/`baseline`; второго
хранилища и офлайн-записи нет.

Add/delete меняют desired и синхронизируют отдельные правила ресурсов через
append/remove, без полной пересборки routing и без рестарта Xray. Правила
добавляются в конец после статических. Удаление уже загруженной записи USERLIST
начинает действовать при очередном обновлении геобаз; direct-исключения нет.
`applied`/`applied:true` подтверждает применение overlay, но не запись в
`geosite_user.dat`/`geoip_user.dat`: файлы USERLIST обновляются при `geodata update`. Каждый успешно
загруженный после restart файл обновляет свой baseline; затем восстанавливается overlay. При
`domain_runtime_sync_failed` или `domain_runtime_apply_failed` desired мог
сохраниться — перечитайте `proxy-domain list` и выполните явный
`proxy-domain apply` после исправления; мутацию автоматически не повторяйте.
Подробный контракт — в [API](docs/API.md) и [эксплуатации](../docs/OPERATIONS.md).

## Обновление геобаз

`geodata update` выполняет две независимые попытки: скачивание внешних GeoSite/GeoIP
с SHA256 и сборку пользовательских баз из SQLite. У каждого процесса свой
`xray run -test`; ошибка одного файла не отменяет допустимые результаты других.
В конце — один restart Xray при заменах; сбой restart не откатывает геобазы и
показывается как ошибка шлюза. Прерванная активация доступна для повторной попытки.

Источники, лимит и расписание принадлежат TOML и редактируются через web/API.
Отсутствующие ключи получают defaults, явные значения сохраняются. Следующий
цикл перечитывает TOML; настройки геобаз из старой БД не используются.
`geodata.builder` меняется только вручную в TOML. На главной панели — даты
успешного и следующего запуска; ошибка раскрывается до этапа и записи журнала.

## Конфигурация

Полный конфиг версии — [templConf/config.toml](templConf/config.toml), установленный как
`/usr/share/xray-core-helper/templConf/config.toml`. Пользовательский
`/etc/xray-core-helper/config.toml` содержит только переопределения:
helper сначала читает заводской файл, затем накладывает пользовательские ключи.
Списки заменяются целиком; явные `false`, пустые строки и списки сохраняют свой
смысл. Результат проходит обычную валидацию. Отсутствующий или неполный заводской
файл — ошибка, запасных значений в Go нет.

Сохранение через setup/API записывает только отличия в изменяемом разделе.
Значение, равное default, удаляется из переопределений и следует за defaults
следующих версий. Остальные разделы и их комментарии сохраняются.
Обновление заменяет заводской файл, обычный запуск пользовательский TOML
не переписывает. Старый полный пользовательский TOML сохраняется: helper
не угадывает, какие значения были выбраны намеренно.
[config.example.toml](config.example.toml) — пример пустого пользовательского файла.
SQLite хранит служебное состояние, а не вторую копию конфига Xray.

Web слушает loopback; параметры listener и разрешение изменений принадлежат секции `[web]` helper. Runtime-файл `/run/xray-core-helper/web.env` передаёт web путь socket и временные данные первичной настройки. Он не предназначен для ручного редактирования.
Служба helper использует `Type=notify` и сообщает systemd о готовности после
создания runtime-файла и открытия Unix-сокета. Поэтому зависимая web-служба не
запускается во время внутренней инициализации helper.

## Контракты разработчика

- [API](docs/API.md): проекции, изменения, поколения и safe-apply.
- [Native templates](docs/NATIVE_TEMPLATES.md): аннотации, границы блока и восстановление.
- [Каталог шаблонов](templConf/README.md): рабочие и системные файлы.
- [Contributing](../CONTRIBUTING.md): проверки и правила изменений.

Нельзя добавлять произвольные пути, shell-команды или общий raw JSON API редактирования всего конфига. JSONC изменяется узко с сохранением комментариев и неизвестных полей. Нативные правила принадлежат шаблонам; helper не генерирует за них сетевую политику.

Beta не реализует разграничение всех API по отдельным ролям клиентов socket. Доступ к socket доверенный; web не имеет HTTP-аутентификации.


### Редактор подключений

Helper поддерживает создание, чтение выбранного подключения, редактирование,
явную замену и удаление outbound через общий API и CLI `outbound`.
Native-типы берутся из Xray-core; URI импортирует `libXray/share`, закреплённый
в go.mod. Сборка требует Go 1.27.2. Xray внутри helper не запускается.
Контракты, правила credentials и примеры CLI — в [API](docs/API.md#подключения-outbound-o14).
Ручная матрица включает 13 типов; фактическую применимость параметров проверяет
установленный Xray. Импорт создаёт только черновик, а не меняет существующий proxy.
