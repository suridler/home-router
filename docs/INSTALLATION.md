# Установка и обновление

Команды устанавливают файлы и перезапускают Helper/web. Сеть включается отдельным
подтверждаемым шагом. Для сетевых изменений нужна независимая консоль.

## Требования

- Linux с systemd, nftables и policy routing; bundles для amd64/arm64.
- Установленный Xray и его systemd unit, доступные assets. Загрузчик Helper
  Xray не устанавливает; API/config проверяет и подготавливает отдельный setup.
- curl и sha256sum. Python 3.9+ нужен bootstrap без явной `--version` для выбора
  версии из публичного GitHub. `gh`, токен и доступ к приватному репозиторию не нужны.
- Для web — Node.js 18+ и npm; CI использует Node 22. CLI-only не требует Node.
  Node/npm также нужны для обновления установленной панели: зависимости готовятся
  в staging до остановки служб.
- Native `sysctl --dry-run --load`; отсутствие поддержки блокирует apply.

Go при установке готового релиза не нужен. Системные зависимости устанавливают
средствами ОС, не загрузчиком проекта.

## Подготовить Xray

Сохраните vendor/admin unit, не заменяйте его примером из repo. Проверьте:

```bash
sudo systemctl show --no-pager xray.service \
  -p ExecStart -p EnvironmentFiles -p PassEnvironment -p UnsetEnvironment
sudo systemctl show xray.service -p Environment --value |
  python3 -c 'import shlex,sys; print("\n".join(v for v in shlex.split(sys.stdin.read()) if v.startswith("XRAY_LOCATION_ASSET=")) or "XRAY_LOCATION_ASSET не задан")'
```

Не публикуйте полный Environment: он может содержать секреты. Assets должны
быть явно указаны сервису. Если переменная отсутствует, найдите реальные файлы:

```bash
sudo find /usr/local/share /usr/share -maxdepth 3 -type f \
  \( -name geoip.dat -o -name geosite.dat \) -print
```

Если оба файла находятся в `/usr/local/share/xray`, добавьте отдельный drop-in.
Не затирайте уже существующий одноимённый файл:

```bash
sudo install -d -m 0755 /etc/systemd/system/xray.service.d
sudo sh -C -c 'cat > /etc/systemd/system/xray.service.d/20-assets.conf' <<'EOF'
[Service]
Environment=XRAY_LOCATION_ASSET=/usr/local/share/xray
EOF
sudo systemctl daemon-reload
```

Для управления геобазами текущая версия поддерживает каталоги
`/usr/local/share/xray` и `/var/lib/xray-core-helper/geodata`; другое расположение
требует отдельной доработки, а не подстановки примерного пути. Drop-in меняет
определение unit, но не перезапускает Xray. Поддерживаются trusted root-owned пути без symlinks,
direct ExecStart с одним config и ограниченный синтаксис environment files.
Wrapper/confdir/неоднозначность отклоняются.

## Переход со старых скриптов на helper

Для рабочего сервера сначала проверьте тот же bundle на disposable экземпляре
с копией конфигурации без секретов. Установка bundle и сетевой setup — разные
операции; успешный installer не подтверждает совместимость старых правил.

1. Зафиксируйте текущие пути Xray/config/assets из сервиса, рабочие порты/марки,
   native-файлы и задания старых скриптов. Проверьте systemd timers и cron, включая
   пользовательские задания. Перед установкой остановите прежние задания записи вручную; U6
   не отключает произвольные cron и старые скрипты.
2. Сохраните приватную резервную копию config, assets, native-файлов, units/drop-ins
   и старого списка доменов, а также способ возврата к прежним скриптам. U6 сохраняет комплект helper и согласованные данные перед заменой,
   но не восстанавливает старые скрипты и их расписания; uninstall сохраняет
   данные и не заменяет откат.
3. На время переноса задайте `geodata_update_enabled = false` в `[scheduler]`
   до запуска helper. Отключите конкретные старые задания записи перед передачей
   управления helper: у config/assets/динамических правил должен остаться один
   владелец. Сначала проверьте явное обновление геобаз, затем включите ежедневное
   расписание.
4. Разберите существующее постоянное правило пользовательского geosite до setup.
   Helper ожидает `proxy-domains-permanent` → `proxy` со ссылкой
   `ext:geosite_user.dat:USERLIST` (либо настроенным именем). Старый
   `ext:geosite_IR.dat:PROXY` отличается и именем файла, и категорией:
   одного переименования файла недостаточно. Не удаляйте действующее правило
   до подготовки и проверки замены. Неоднозначный вариант setup отклоняет.
5. Старый список перенесите вручную через `proxy-domain add ДОМЕН` после подготовки
   API и постоянного правила. SQLite desired/baseline не заполняется из старого
   `.dat` или текстового файла. Сверьте `proxy-domain list` с исходным списком;
   автоматического импорта нет.
6. Сохраните рабочий proxy, просмотрите кандидат и native diff перед apply.
   Принятие существующего Xray без подготовки сети сохраняет файлы, но само
   по себе не создаёт недостающие API, binding и постоянное правило доменов.
   После применения выполните [приёмку](TESTING.md), включая повторный запуск
   helper, восстановление доменов, обновление геобаз и тест с LAN-клиента.

До реализации общей web-авторизации оставляйте панель на loopback и используйте
SSH tunnel. Первичная настройка выполняется через `sudo xray-core-helper setup`;
панель не является общей границей авторизации.

## Установить release

Релизы публикуются в публичном GitHub `suridler/home-router`; авторизация `gh`
и токен не нужны. Загрузчик — тонкий bootstrap: определяет Linux amd64/arm64,
скачивает raw CLI выбранной версии и общий `SHA256SUMS`, проверяет SHA256 и
запускает `xray-core-helper install`. Архив целиком bootstrap не распаковывает.
`SHA256SUMS` содержит четыре платформенных asset: два архива и два raw CLI.

```bash
VERSION=helper-vX.Y.Z
BOOTSTRAP_DIR=$(mktemp -d "$HOME/xray-helper-bootstrap.XXXXXXXX")
curl --fail --silent --show-error --location --proto '=https' \
  --tlsv1.2 --output "$BOOTSTRAP_DIR/install-from-github.sh" \
  "https://github.com/suridler/home-router/releases/download/$VERSION/install-from-github.sh"
sudo bash "$BOOTSTRAP_DIR/install-from-github.sh" --version "$VERSION"
```

Просмотрите release notes. Bootstrap проверяет SHA256 raw CLI по `SHA256SUMS`;
установщик проверяет version, ELF architecture и три бинарника архива (CLI,
daemon, сборщик geosite). Fallback на сборку отсутствует. `--without-web` выбирает CLI-only на чистом
хосте, `--with-web` — web. Без `--version` выбирается максимальная опубликованная
SemVer (draft исключаются); beta можно указать явно. Явная версия может быть
новее, старше или совпадать с установленной, если это допускает
`minimum_installable_version` текущего комплекта.

`--recover` не обращается к сети или GitHub: проверяет сохранённые
`/var/lib/xray-core-helper-update/installer` и `installer.sha256` (root, 0700/0600)
и запускает `install --recover`, предлагая повтор или откат. Если сохранённого
установщика нет, bootstrap завершается ошибкой и не выбирает другой релиз.
Установщик, журнал операции, кандидат и снимок находятся вне заменяемых каталогов.

## Настройки helper: defaults и переопределения

Заводской полный TOML находится в
`/usr/share/xray-core-helper/templConf/config.toml` и обновляется с комплектом.
В `/etc/xray-core-helper/config.toml` записываются только пользовательские
отличия; отдельной рабочей копии defaults в `/etc/…/templConf` нет.
Пустой пользовательский файл допустим. Явное сохранение default удаляет ключ
из переопределений; при обновлении такой параметр получает новое default.
Старый полный пользовательский TOML установщик сохраняет без догадок об авторстве
значений. Переименование ключей не выполняется автоматически.

Standalone preflight до установки читает defaults из скачанного комплекта.
Для запуска CLI напрямую из распакованного комплекта передайте путь явно:
`xray-core-helper -defaults /path/to/bundle/xray-core-helper/templConf/config.toml -config /path/to/overrides.toml installation-settings`.
Установленный CLI и daemon по умолчанию читают заводской файл из `/usr/share`.
Отсутствующий или неполный файл не заменяется встроенными значениями.

## Пройти setup

Установщик выполняет discovery, создаёт свой path-permissions drop-in, запускает
Helper и в терминале открывает пошаговый CLI setup. LAN-ключей у установщика нет.
Standalone setup останавливает helper/web, берёт runtime lock и работает в процессе
без запросов к socket; после завершения возвращает прежнее состояние служб.
`setup --status` остаётся обычным чтением через socket. Пока операция U6 не
завершена, setup отклоняется. Без TTY setup откладывается:

```bash
sudo /usr/local/bin/xray-core-helper setup
```

1. Продолжить настройку helper для установленного Xray либо настроить позже.
   Анализ конфигурации выполняется автоматически.
2. Выбрать, нужна ли настройка перенаправления трафика через Xray (TProxy).
   Удалённый прокси можно подключить позже.
3. Выбрать интерфейс, адрес сервера и подсеть. Единственный вариант предлагается
   по Enter; при нескольких интерфейсах или адресах требуется явный выбор.
4. Просмотреть краткий план. Пункт «Подробнее об изменениях» показывает порт,
   марку и изменяемые разделы Xray, не применяя настройки.
5. Явно подтвердить подготовку, затем отдельно включить перенаправление.
6. Просмотреть результаты проверок интернета до и после включения, проверить
   соединения других устройств и явно сохранить настройки до указанного срока.
   Сохранение включает автозапуск. Можно повторить проверку, сохранить настройки
   даже при её неуспехе, откатить изменения или дождаться автоматического отката.

Enter на шагах подготовки, включения и сохранения не подтверждает изменения.
Отказ шлюза отвечать на ping показан отдельно от успешности HTTPS.
Время проверки и срок подтверждения выводятся в часовом поясе сервера.

Явное принятие существующего Xray без подготовки сети сохраняет config/сеть.
При пустом config создаётся кандидат из шаблона. Наличие config само по себе
не означает завершённый Helper setup.

Параметры выбранной сети сохраняются в `[network]` файла `config.toml` helper:
`interface`, `address`, `ipv4_prefix`. Там же задаются марка перехвата
`intercept_mark` (по умолчанию `1`) и таблица маршрутизации `policy_table`
(по умолчанию `100`). Порт и исходящая марка читаются из конфигурации Xray,
GID — из службы Xray. Заводские native-шаблоны содержат placeholders;
setup формирует конкретные проверяемые файлы. Сохранение TOML входит в общую
транзакцию подготовки и её откат. После ручного изменения TOML нужен restart
helper и явное применение шаблонов; запуск helper сам сеть не меняет.

При подготовке сети setup добавляет постоянное правило `proxy-domains-permanent`
со ссылкой на `<user_geosite>:USERLIST` после специальных системных правил,
перед пользовательскими. Если файла нет, собирается начальная геобаза с техническим
доменом `.invalid`; существующий файл сохраняется. Проверка использует временный
набор assets; новая геобаза устанавливается перед конфигом Xray и удаляется при
откате setup. Неоднозначное существующее правило требует ручной проверки.

Внутренний планировщик helper каждые 30 секунд
проверяет смену запуска Xray и при необходимости восстанавливает динамические
правила из desired/baseline SQLite. После restart возможна пауза до следующего
тика; при недоступном API повтор происходит позже. Остановленный Xray не запускается.
Ручная проверка: `sudo xray-core-helper proxy-domain reconcile`.

Начальные proxy/direct разделены, но могут оба использовать freedom:
удалённый proxy ещё нужно настроить. Подготовка не включает interception.
CLI включает boot enable после confirm; web предлагает отдельное подтверждение.

## Открыть web и проверить

По умолчанию web слушает `127.0.0.1:3000` на Linux-хосте. Для удалённого хоста:

```bash
ssh -N -L 3001:127.0.0.1:3000 user@server
```

Откройте `http://127.0.0.1:3001/`. Начальную настройку выполняйте в консоли через
`sudo xray-core-helper setup`; панель показывает инструкции и состояние.
Проверки состояния: [Эксплуатация](OPERATIONS.md).

## Установить из исходников

Это путь разработки. Требуются Go версии из go.mod и Node/npm для web.
Из корня repo:

```bash
sudo bash xray-core-helper/packaging/install-bundle.sh
```

Для CLI-only используйте `--without-web`. Флаг `--prebuilt` применяется к
проверенному bundle и теперь передаёт управление
`bin/xray-core-helper install --bundle ROOT`; ручной `npm ci` не нужен. Node/npm
всё равно должны быть установлены: updater готовит web-зависимости в staging.
Исходная shell-сборка остаётся инструментом разработки и не является U6 updater.
Ручная установка нескольких unit-файлов не заменяет discovery и создание
разрешений установщиком.

Оба способа устанавливают закреплённый `domain-list-community` в
`/usr/local/bin/domain-list-community`: он нужен для сборки динамического списка
при обновлении геобаз. В release он уже собран; установка из исходников собирает
его через Go из проверенного модуля. Пользовательский `geodata.builder` в
существующем config сохраняется; нестандартный путь обеспечивает администратор.

Размер каждого файла геобазы задаётся в `[geodata].max_asset_size_mb`: по умолчанию
256 МБ (1 МБ = 1024 × 1024 байт). Например, `max_asset_size_mb = 512` задаёт 512 МБ.
Новый цикл обновления использует изменённый лимит без restart helper. Один
лимит действует при загрузке, проверке кандидатов и замене файлов. Setup
читает его из TOML при запуске. Проверки SHA256 внешних файлов обязательны;
отдельный небольшой лимит файлов контрольных сумм не изменён.

Имя пользовательского geosite задаётся в `[geodata]`:

```toml
user_geosite = "geosite_user.dat"
```

Разрешено имя `geosite_*.dat` без пути. После изменения перезапустите helper;
переименование существующего файла выполняет администратор. Явно помеченная
ссылка `ext:ИМЯ:КАТЕГОРИЯ` получает имя из настройки при подготовке/apply конфигурации,
через штатную проверку и подтверждение. Перезапуск helper не меняет Xray.
Без binding-аннотации ссылка остаётся ручной. Автоматической миграции старых файлов
нет. Не меняйте имя при
pending/recovery: завершите операцию с прежним значением, затем меняйте настройку.
Пользовательский geoip задаётся `user_geoip = "geoip_user.dat"` (`geoip_*.dat`);
он собирается из IPv4 динамического списка в категорию USERLIST. Обычные загружаемые `geosite.dat` и `geoip.dat` не переименовываются.

## Обновление установленного комплекта

До обновления проверьте safe-apply status и `setup --status`. Завершите pending
старой версией; незавершённые config/DB/geodata/consolidation блокируют prepare.
Helper/web/units/factory assets обновляются одним согласованным bundle.
Обновление не запускает setup, не меняет Xray config/сеть и не перезапускает
Xray/TProxy; setup и сеть остаются отдельными операциями.

```bash
sudo xray-core-helper update check
sudo xray-core-helper update status
sudo xray-core-helper update prepare helper-vX.Y.Z
# prepare возвращает operation.id; ID попытки выбирает клиент (32 lowercase hex)
ACTION_ID=$(openssl rand -hex 16)
sudo xray-core-helper update apply OPERATION_ID "$ACTION_ID"
sudo xray-core-helper update retry OPERATION_ID NEW_ACTION_ID
sudo xray-core-helper update rollback OPERATION_ID NEW_ACTION_ID
```

`apply`, `retry` и `rollback` требуют явные operation ID и action ID; повтор с тем
же action ID идемпотентен, новое действие получает новый ID. Автоматического
повтора и автоматического отката нет. `retry`/`rollback` доступны после `failed`
или `interrupted`; rollback требует готового снимка. Если daemon недоступен,
повторите bootstrap с `--recover`: он использует сохранённый installer без сети.

`check` обращается к публичному GitHub без токена, исключает draft и выбирает
максимальную SemVer, включая prerelease; ошибка API показывается как ошибка, а не
как «обновлений нет». Точная версия может быть новее, старше или совпадать с
установленной. Нижняя граница — необязательное поле
`minimum_installable_version` в schema1 `/usr/share/xray-core-helper/release.json`;
без поля ограничения нет. Проверка выполняется до замены файлов и без daemon,
поэтому её не обходит bootstrap. Откат возвращает согласованный снимок файлов и
данных и не является обычной установкой старой версии поверх новой БД.

`prepare` скачивает архив и `SHA256SUMS`, проверяет manifest, SHA256, ELF
architecture и место; для web заранее выполняет `npm ci` в staging. При запуске
через API сохраняется проверенная копия текущего installer и подготавливается
(stage) целевой архив; эта копия используется для worker. Bootstrap использует
raw CLI целевой версии. Сервисы останавливаются только на `apply`; worker
запускается через `systemd-run`.
После успешной проверки запускаются helper/web. Журнал операции, проверенный
installer, кандидат и снимок хранятся в `/var/lib/xray-core-helper-update` — вне
восстанавливаемых каталогов; не удаляйте их до завершения операции. При
повреждённом или неполном снимке откат отклоняется.

Обновление сохраняет наличие установленной панели (не добавляет и не удаляет её),
настройки в `/etc/xray-core-helper` и данные в `/var/lib/xray-core-helper`: TOML,
SQLite, backups, дополнительные пользовательские файлы и администраторские drop-in.
Заменяются четыре поставляемых рабочих шаблона в `/etc/xray-core-helper/templConf`, заводской
`/usr/share/xray-core-helper/templConf`, принадлежащие установщику units и, если
панель установлена, `/opt/xrayui-web`; собственный drop-in
`20-installation-paths.conf` пересоздаётся. После прерывания daemon поднимает
минимальный recovery API: `/v1/health`, `/v1/web/settings` и `/v1/update`, остальные
обычные изменения заблокированы до retry/rollback.

Обновление шаблонов не применяет их к системным файлам. Пользователь рассматривает
расхождения и явно выбирает apply либо accept-system. Откат обновления возвращает
предыдущие шаблоны. Перенос параметров старой версии — отдельная задача миграции.

Локальные тесты не заменяют U6.12: два реальных release, upgrade/downgrade,
retry/rollback и восстановление после fault injection на сервере ещё не
выполнялись. Это операторская приёмка, а не автоматическая проверка.

`packaging/uninstall-bundle.sh` сохраняет конфигурации и данные. Для clean-install
нужен новый disposable host или исходный snapshot, а не один удалённый config/DB.

### Расписание обслуживания

Helper собирает ошибки каждые 20 секунд и проверяет восстановление динамических
правил каждые 30 секунд. Отдельные systemd timer/oneshot для этих задач и геобаз
больше не устанавливаются; обновление bundle отключает и удаляет прежние units.
Если прежняя задача ещё выполняется, установщик останавливается: дождитесь её
завершения и повторите установку. Аварийный rollback timer остаётся внешним.

```toml
[scheduler]
geodata_update_enabled = true
geodata_update_time = "04:00"
```

Обновление геобаз выполняется ежесуточно по времени сервера. Для отключения
укажите `false`; изменение учитывается в течение минуты без restart helper. На чистой установке
первый запуск — в ближайшее указанное время. Дедлайн сохраняется в SQLite:
после простоя выполняется один пропущенный запуск, затем обычное расписание.
