### M13 — единая схема настроек helper: defaults и переопределения

Согласовано 21.10.2026: полный текстовый конфиг поставляется в templates
и обновляется вместе с версией helper. Пользовательский config.toml хранит
только явно переопределённые пользователем значения. Итоговые настройки —
полный конфиг с наложенными пользовательскими значениями.
Реализовано в рабочем дереве; серверная установка этого изменения ещё не выполнялась.
Заводской файл читается напрямую из
`/usr/share/xray-core-helper/templConf/config.toml`; пользовательский файл —
`/etc/xray-core-helper/config.toml`. Отдельной рабочей копии defaults нет.

1. Полный TOML в templates — единый источник значений по умолчанию;
   не поддерживать независимо дублирующий набор defaults в Go.
2. Общая загрузка для daemon, standalone setup/install и всех settings API:
   сначала полный TOML, затем пользовательские ключи, затем проверка результата.
   Явные false, 0, пустые строки и списки не считать отсутствующим значением.
3. Единый механизм сохранения пользовательских переопределений для всех
   разделов. Не сериализовать весь эффективный конфиг при изменении одного
   параметра и не материализовывать посторонние defaults в config.toml.
4. При обновлении заменять полный конфиг templates, сохранять пользовательский
   config.toml. Обычный запуск не переписывает пользовательский файл.
5. Для действующего полного config.toml невозможно автоматически определить,
   какие значения пользователь выбрал сам, а какие записал прежний helper.
   Порядок перехода согласовать отдельно; не удалять настройки по догадке.
6. При сохранении значение, совпадающее с default установленной версии,
   удаляется из пользовательского config.toml. Такой параметр далее следует
   за defaults следующих версий; отдельного закрепления равного значения нет.
   Сброс к default также удаляет пользовательское переопределение.
7. Проверить наложение вложенных секций, замену списков, сохранение явных
   false/0/empty, одинаковую загрузку всеми читателями, точечное сохранение,
   обновление defaults без изменения overrides и восстановление комплекта.

Аудит defaults: набор значений удалён из Go, включая fallback лимита геобаз,
имён пользовательских файлов, сетевых параметров и путей при выборе файловых
логов. В коде остаются правила валидации, протокольные ограничения и фиксированные
пути установки/идентификаторы управляемых файлов: они не подставляют настройки.
Полнота заводского TOML проверяется для каждого поля, в том числе false/empty.

Автоматическая миграция при установке/обновлении не согласована: пользователь
выбрал другое направление. Прежнее предложение versioned migration hooks
не является принятым планом. Переименование/удаление ключей требует отдельного
решения; наложение defaults само по себе такие изменения не решает.

### O14 — управление всеми типами outbound

Статус: **O14.1–O14.7 реализованы локально; O14.8 — локальные проверки пройдены, серверная приёмка открыта** (21.10.2026).
Согласованы импорт ссылки и ручная настройка. Оба способа используют типы
libXray/его зависимости Xray-core и существующую конфигурационную транзакцию
helper; отдельную полную модель протоколов в helper не создаём.
Реализованы общий native-редактор, web и CLI для 13 типов; импорт использует
libXray/share. Изменения M13 в рабочем дереве сохранены.

#### Источники и границы

- Выбранный парсер импорта — [XTLS/libXray, пакет share](https://github.com/XTLS/libXray/tree/main/share),
  указанный в README Xray-core. Лицензия — MIT. Историческое совпадение с ранее
  обсуждавшимся источником не подтверждено, но возможности проверены по исходникам.
- В [parse_share.go](https://github.com/XTLS/libXray/blob/main/share/parse_share.go)
  представлены VLESS, VMess, Shadowsocks, SOCKS, Trojan, Hysteria2.
  README исключает legacy VMess Base64(JSON); поддержку такого формата нельзя
  обещать только на основании наличия VMess в списке.
- Текущий [go.mod libXray](https://github.com/XTLS/libXray/blob/main/go.mod)
  требует Go 1.27.2 и Xray-core. Сборка helper переведена на Go 1.27.2
  при подключении pinned share.
  Плавающий main и собственная копия парсера не используются.
- Матрица полного ручного редактора строится по
  [outboundConfigLoader Xray 26.10.17](https://github.com/XTLS/Xray-core/blob/92ccc939aaf4/infra/conf/xray.go):
  VLESS, VMess, Trojan, Shadowsocks, SOCKS, HTTP, WireGuard, Hysteria,
  MASQUE, Freedom, Blackhole, DNS и Loopback; direct/block — aliases.
  Область включает settings протокола и применимые streamSettings, security,
  sockopt, mux, sendThrough и цепочки outbound. Наличие типа в этой матрице
  не означает наличие стандартного формата ссылки для импорта.
- Подписки, автоматическое переключение резервных подключений, редактирование
  inbounds и общий raw JSON editor в O14 не включены.

#### O14.1: матрица и оценка зависимости

Проверенный кандидат — libXray
[`75ccb623c807a1113a064278e3e544b0049c16a5`](https://github.com/XTLS/libXray/tree/75ccb623c807a1113a064278e3e544b0049c16a5/share),
MIT, Go 1.27.2, зависимость от Xray-core `92ccc939aaf4` (26.10.17).
Это совпадает с ранее установленным core; плавающий main не используется.
В основной go.mod библиотека закреплена как v1.261017.0 (тот же commit). После сравнения альтернатив
пользователь согласовал прямой импорт только пакета `share` через адаптер helper.
Рост бинарника примерно на 23 МБ принят ради сопровождения URI-форматов upstream.
Ручное редактирование всех outbound остаётся отдельным механизмом общей модели;
ограничения URI-парсера не сокращают матрицу ручного редактора.

| Outbound | Основные ручные поля settings | Импорт libXray/share |
| --- | --- | --- |
| VLESS | адрес, порт, ID, encryption/flow, reverse, уровень/email | vless URI |
| VMess | адрес, порт, ID, security, уровень/email | vmess URI; legacy Base64(JSON) не поддерживается |
| Trojan | адрес, порт, password, flow, уровень/email | trojan URI |
| Shadowsocks | адрес, порт, method/password, уровень/email | ss URI |
| SOCKS | адрес, порт, user/pass, уровень/email | socks URI; авторизация Base64(user:pass), plain user:pass отклоняется |
| HTTP | адрес, порт, user/pass, headers, уровень/email | Нет |
| WireGuard | secretKey, address, peers, mtu, reserved, remoteDNS, noKernelTun | Нет |
| Hysteria | version, address/port; авторизация и транспорт в streamSettings | hy2/hysteria2 URI |
| MASQUE | address/port, remoteDNS; параметры соединения в streamSettings | Нет |
| Freedom | targetStrategy/domainStrategy, redirect, fragment/noises, proxyProtocol, ipsBlocked/finalRules | Нет |
| Blackhole | response | Нет |
| DNS | адрес/порт/сеть, rewrite-поля, rules, nonIPQuery/blockTypes, userLevel | Нет |
| Loopback | inboundTag, sniffing | Нет |

Таблица определяет реализованную ручную матрицу редактора; серверная приёмка остаётся отдельной. Схемы
полей берутся из указанной версии core, включая существующие массивы серверов
и новые плоские поля. Общие параметры: tag, sendThrough, targetStrategy,
proxySettings, mux, streamSettings/sockopt. Матрица транспорта core включает
RAW/TCP, XHTTP/SplitHTTP, mKCP, gRPC, WebSocket, HTTPUpgrade, Hysteria, MASQUE
и XDrive. Наличие транспорта не означает готовую полную поддержку его параметров
в URI-парсере. Старые HTTP/H2/H3 и QUIC transport удалены; это не запрещает
HTTP/2 и HTTP/3 внутри XHTTP. TLS/Reality/none применяются по ограничениям
выбранного протокола и core; WireGuard имеет собственную схему соединения.

Изолированная сборка CLI тем же Go 1.27.2, CGO=0, trimpath и `-s -w`:

| Показатель | Без share | С share |
| --- | ---: | ---: |
| Бинарник, байт | 13 975 712 | 38 039 712 |
| gzip, байт | 5 867 490 | 14 626 513 |
| Нестандартные пакеты в графе сборки | 79 | 499 |
| Модули в графе, включая helper | 11 | 56 |

Причина роста — прямое использование share конфигурационных типов и Build
Xray-core. Эти вызовы проверяют конфигурацию, но не запускают Xray внутри helper.
Парсер также принимает списки/подписки, пропускает невалидные элементы и не
сообщает обо всех неизвестных URI-параметрах. Для O14 потребуется ограничение
одной ссылкой. Согласовано следовать поведению библиотеки: показывать результат
импорта и общее предупреждение об ограничениях, без собственного перечня
URI-параметров и обещания перечислить всё проигнорированное. Преобразование share содержит
проекцию полей: оно не подходит для сохранения произвольного существующего
outbound при ручном редактировании.

Рассмотренные варианты (выбран вариант 1):

1. Прямой pinned share: минимальный собственный код импорта, но увеличивает
   бинарники и поднимает toolchain. Существующая внешняя проверка `xray run -test`
   остаётся; внутренняя Build библиотеки её не заменяет.
2. Расширить существующий parser helper: stdlib URL/Base64 и единая typed-модель,
   реальная проверка существующим Xray. Нет зависимости от core внутри helper,
   но поддержку URI-диалектов и fixtures нужно сопровождать самостоятельно.
3. Адаптировать MIT-код share без conf/Build: сохранить attribution, заменить
   core-типы общей моделью helper. Это уже собственная поддерживаемая копия,
   а не готовая обновляемая зависимость; цена сопровождения выше прямого импорта.
4. Отдельный конвертер на libXray: сохраняет размер daemon, но добавляет бинарник,
   протокол вызова и доставку; общий комплект не становится меньше. Без отдельной
   потребности в изоляции не предпочтительнее прямого импорта.

Дополнительно проверены sing-box, Proxylink, vpnparser и XrayKeyParser.
В официальном sing-box не найден готовый парсер нужных URI; у остальных
обнаружены пробелы поддержки, ошибки разбора или недостаточное сопровождение.
Они не выбраны: адаптация потребовала бы собственной поддержки форматов.

#### Согласованные решения

Типы подключения переиспользуются из libXray и его зависимости Xray-core.
Обвязка helper ограничена разбором одной ссылки, безопасной диагностикой,
оболочкой API и интеграцией с существующими проверкой/записью. Собственную
иерархию типов протоколов не вводить. При ручной правке существующего конфига
сохранять неизвестные поля и JSONC-комментарии: не выполнять полный round-trip
через проекцию share или типы, отбрасывающие неизвестные поля.

1. Разрешено редактировать подключение и протокол штатного `proxy`, сохраняя
   тег и существующие ссылки routing/DNS. Это не разрешение удалять системные теги.
2. Поведение редактора взять за основу из 3x-ui. Проверена ревизия
   `a8d0700bf2ed06d77c077fc45fc0387d9abdbaab`:
   [OutboundFormModal](https://github.com/MHSanaei/3x-ui/blob/a8d0700bf2ed06d77c077fc45fc0387d9abdbaab/frontend/src/pages/xray/outbounds/OutboundFormModal.tsx)
   заполняет форму существующим outbound. В нашем O14 импорт ограничен новым
   черновиком: импорт поверх существующего outbound запрещён.
   [Adapter](https://github.com/MHSanaei/3x-ui/blob/a8d0700bf2ed06d77c077fc45fc0387d9abdbaab/frontend/src/lib/xray/outbound-form-adapter.ts)
   передаёт реальные UUID/пароли/ключи в поля; в
   [TrojanFields](https://github.com/MHSanaei/3x-ui/blob/a8d0700bf2ed06d77c077fc45fc0387d9abdbaab/frontend/src/pages/xray/outbounds/protocols/trojan.tsx)
   пароль представлен обычным Input, а не признаком «задано».
   В O14 существующие значения доступны для просмотра и изменения в явном
   редакторе выбранного подключения; импорт заполняет форму нового черновика,
   сохранение применяет её значения. Пустое поле не означает скрытое сохранение прежнего
   секрета: оно обрабатывается по схеме поля (очистка допустимого или ошибка
   обязательного). Исключение из запрета выдачи секретов ограничено typed
   edit API выбранного outbound при существующих проверках доступа; сводки,
   обычные списки, логи и ошибки секретов не содержат. Ссылки не копируются
   в журналы. Перенос общего JSON-редактора и прочих функций 3x-ui не согласован.
3. Редактирование существующего outbound не меняет его тег и протокол.
   Смена протокола или полная замена подключения — отдельное явное действие
   «Заменить подключение» с перечнем заменяемых настроек. При замене сохраняются
   **только тег и обязательные привязки helper** (включая исходящую марку
   обхода TProxy). Остальные настройки берутся из нового черновика; прежние
   settings, транспорт, TLS/REALITY, mux, sendThrough и цепочка подключения
   автоматически не наследуются. Если их нет в черновике, они удаляются.
   Импорт создаёт новый черновик без записи и restart; замена выбранного
   outbound этим черновиком требует отдельного явного подтверждения.
   Существующие ссылки routing/DNS на сохранённый тег не переписываются.

### O15 — проверка подключения до применения

Статус: **идея согласована; планируется после O14** (21.10.2026).
Источник идеи — [meteroer/xray-go: проверка через временный прокси](https://github.com/meteroer/xray-go/blob/2cfeaf0bedd5766e52159b9a4f2d26dbf5ea5324/latency/tester.go).

- В редакторе outbound пользователь импортирует или вводит подключение,
  запускает проверку и видит результат до сохранения.
- Проверять кандидат отдельным временным процессом установленного Xray
  с SOCKS на loopback, выполняя HTTPS-запрос через него. Действующий Xray,
  его конфиг, службы, nftables и policy routing не изменять.
- Использовать общую модель O14; показать успешность, длительность и понятную
  причину ошибки. Проверять ожидаемый HTTP-статус, а не только получение ответа.
  Проверка подключения не подтверждает прохождение LAN/TProxy-трафика.
- Ограничить время выполнения; при успехе, ошибке или отмене завершать временный
  процесс и удалять временные файлы. Учётные данные не выводить в журналы.
- Автоматический выбор узлов, failover и подписки в этот пункт не входят.
- До реализации уточнить состав временного конфига, использование DNS/геобаз
  и исходящей марки в действующей TProxy-схеме, чтобы запрос действительно
  проверял выбранное подключение и не перехватывался повторно.

Критерий завершения: общий API проверки и действие в редакторе; проверены
успех, отказ подключения, неверный HTTP-статус, timeout, отмена и очистка;
подтверждено отсутствие изменений действующей конфигурации и маршрутизации.

### G10 — упрощение обновления геобаз и диагностики

Статус: **реализован и проверен локально; серверная приёмка отдельно**
(21 октября 2026 года). Перед реализацией создан локальный commit `63a050d`
с предыдущими CLI/safe-apply изменениями и согласованным планом.
Прежний общий транзакционный откат удалён. Базовая G10 доставлена на рабочий
сервер в beta.5; обнаруженный отказ runtime routing привёл к G10.9. Доработки
G10.8/G10.9 опубликованы в beta.6; обновление через web, геобазы и динамические
правила на установленной версии подтверждены пользователем 21.10.2026.
Расширенная матрица отказов остаётся отдельной приёмкой.
Результаты проверок и оставшаяся установленная приёмка — в TESTING.
При смене имени USERLIST новый файл собирается, но baseline и динамические
правила сохраняются до подключения файла в постоянном proxy-правиле Xray.
DNS-ссылка сама по себе не активирует baseline; ожидание binding не вызывает
повторных перезапусков. Проверено локальной регрессией.
Делегирование DeepSeek в этом блоке не выполнялось: доступного исполнителя
в текущем сеансе нет; реализация, ревью и проверки выполнены Codex.

Согласованные решения:

- TOML — единственный источник настроек геобаз: источники, checksum, origins,
  builder, имена пользовательских баз, лимит размера и расписание. API/панель
  читают и сохраняют TOML; builder меняется только вручную в TOML, в панели
  доступен для просмотра. Операция получает один снимок настроек. БД хранит
  ресурсы пользователя, состояние исполнения и ошибки, а не вторую конфигурацию.
- Перенос настроек из БД не нужен, в том числе вручную. При отсутствии ключа
  в TOML использовать стандартное значение helper для этого ключа; частично
  заполненный раздел дополняется defaults только для отсутствующих параметров.
  Явно заданные значения не перезаписывать и не считать отсутствующими. Одни
  и те же эффективные настройки использовать в панели, CLI и scheduler.
  Defaults источников и origins должны быть согласованы; не возвращать скрытую
  зависимость доступности обновления от старых настроек БД.
- Есть два независимых процесса: скачивание внешних geosite/geoip и сборка
  пользовательских geosite/geoip из ресурсов. В одном цикле выполняются оба,
  последовательно; ошибка первого не препятствует попытке второго.
- Внутри процесса файлы независимы. Ошибка скачивания, checksum, сборки или
  записи одного файла не отменяет допустимый результат другого. Для внешнего
  файла обязательна собственная checksum. Рабочий файл не усекать при записи:
  использовать временный файл и rename, оставляя старый при неудаче этой записи.
- **У каждого процесса свой `xray run -test`**, общий для его geosite/geoip.
  Успешные кандидаты проверяются вместе с оставшимися действующими файлами;
  второй процесс учитывает уже применённые результаты первого. Только провал
  этого теста отклоняет/откатывает весь набор изменений данного процесса;
  он не отменяет успешный результат другого процесса.
- Сохранять временные исходные файлы до завершения проверки/замены процесса.
  При частичной ошибке записи нельзя считать проверенным иной набор файлов:
  при необходимости проверить фактически получившийся набор до перезапуска.
  Общий откат по ошибке записи не вводить. Если восстановление по failed test
  физически не удалось, сообщить критическую ошибку, не скрывать её как штатный отказ.
- После завершения обоих процессов — один restart Xray, только если были
  фактические замены, включая завершение прерванной активации уже заменённых файлов. При неизменных файлах и полностью неуспешных попытках
  без замен restart не нужен. Сбой запуска — критическая ошибка шлюза/Xray,
  отдельно от результатов обновления файлов; автоматического отката баз нет.
- После успешного restart восстановить динамические правила и согласованно
  завершить консолидацию. Не заявлять восстановление runtime до его успеха и
  не терять исходные ресурсы/состояние SQLite при ошибке активации.
- Проверку содержания/правильности категорий доверяем источнику. Не добавлять
  проверки сайтов, семантическую оценку списков, общий health/API gate для
  отката геобаз, хранение «вчерашней» версии или отдельную кнопку отката.
- Одно действие панели **«Обновить геобазы»**, тот же цикл для CLI и scheduler.
  Расписание остаётся ежесуточным, серверное время, default 04:00, с отключением
  через `scheduler.geodata_update_enabled` и временем `geodata_update_time`.
- Главная карточка: зелёный статус, дата/время последнего успешного выполнения
  и следующего запланированного запуска. При отключённом расписании — понятная
  отметка вместо вымышленной даты. Штатные этапы/файлы на главной не показывать.
- Любая ошибка процесса: красный статус, этап и ссылка «Подробнее» с причиной,
  временем и записью журнала. Частичный успех раскрывается там же. Панель и
  журнал связываются одним ID операции и кодом ошибки. Успешный повтор снимает
  текущую ошибку, сохраняя историю. Общее сообщение без причины недопустимо.
- Логировать ошибки с контекстом процесса, файла и этапа, без credentials и
  сырых секретных конфигов. Не спамить журнал штатными тиками/проверками.
  Ошибка очистки временных данных после успешного применения — отдельное
  предупреждение, а не ложный отказ обновления. Никаких автоматических reboot.

| G10.6 | Удалить хранение геонастроек в БД и их наложение на TOML, ставшие ненужными recovery-переходы и дублированные проверки; актуализировать API/OPERATIONS/TESTING | Нет второго источника настроек, общего автоматического отката после restart и недействующих контрактов; неизвестный мусор не удаляется скрыто |

### G10.8 — асинхронный запуск обновления геобаз

Реализовано 21 октября 2026 года; включено в helper-v0.2.0-beta.6.
Проверено: Go test/race/build/vet и 162 теста панели, быстрый HTTP 202,
разрыв запроса, повтор ключа, конфликт запуска, polling и остановка worker.
Обновление установленного сервера через web и проверка геобаз выполнены
по подтверждению пользователя 21.10.2026; сценарии отказов учитываются отдельно.

- `POST /v1/xray/geodata/update` сохраняет операцию и быстро возвращает
  HTTP 202 с ID; не ожидает скачивания, сборки, тестов и restart.
- Исполнение принадлежит daemon helper, не контексту HTTP-запроса. Закрытие
  страницы, разрыв соединения и HTTP timeout не отменяют принятую операцию.
  Отдельная служба, внешняя очередь и WebSocket не нужны.
- Панель опрашивает существующий status endpoint каждые пять секунд и после
  открытия страницы восстанавливает её отображение. Показывает текущий этап,
  затем дату успеха либо ошибку с этапом; недостоверных процентов нет.
- Сохранены idempotency, единственная активная операция, один снимок TOML,
  существующие mutation gates, checkpoint и диагностику прерванного daemon.
  Перезапуск helper не означает автоматический повтор операции.
- CLI и scheduler используют тот же контракт. CLI ожидает завершения
  через polling, но завершение клиента не останавливает принятую задачу.
- Локально проверены быстрый 202, повтор одного ключа, конфликт параллельного запуска,
  disconnect клиента, повторное открытие панели, итоговые ошибки и остановку
  daemon. Ошибку принятия отличать от ошибки уже принятой операции.

Прежний timeout полной отправки routing решается в G10.9 переходом на точечный
append/remove; наращивание бюджета полной пересборки больше не является
следующим шагом. Сохранённые 15 с для CLI Xray и 25 с для routing-задания нужно
оценить на установленной beta.6. Менять их только при подтверждённом отказе,
учитывая полный бюджет операции, без слепых повторов append.

### G10.9 — точечная синхронизация runtime routing

Реализовано и опубликовано в helper-v0.2.0-beta.6; проверка динамических правил
на установленной версии выполнена по подтверждению пользователя 21.10.2026.

Решение 21 октября 2026: использовать точечное добавление в конец через API и
удаление по ruleTag. Ресурс из USERLIST удаляется при очередном обновлении баз;
немедленного direct-исключения и restart при delete нет. Geodata cron не включать.
Статические правила получают приоритет над динамическими; порядок и содержимое
статических правил автоматически не меняются.

Реализация: один детерминированный тег на домен/IPv4, `lsrules` перед diff,
append только отсутствующих ресурсов, удаление только лишних owned tags.
Неизменившиеся ресурсы не удаляются и не добавляются повторно; полной отправки
routing и remove+add одного общего правила нет. Потерянный ответ append
проверяется по фактическим тегам без слепого повторения. Ошибка синхронизации
повторяется внутренним reconciler и при неизменном InvocationID.
Проверки реализации завершены: Go tests/race/build/vet, 157 тестов панели и
изолированная приёмка нового Go-клиента на Xray 26.10.17 прошли. Beta.6 уже
установлена через web, проверка динамических правил подтверждена пользователем.
Панель показывает отложенное удаление из USERLIST.

История исследования (до изменения реализации; перечисленные альтернативы
не являются очередью внедрения). Рабочий Xray уже обновлён с 26.3.27 до
26.10.17; geodata cron включать не решено, выбран append/remove:

- Прежний helper на каждую add/delete отправлял полный routing через `adrules`
  без append. Поэтому перечитываются используемые geosite/geoip-категории,
  даже если изменился один IPv4. Небольшой динамический overlay не отделён
  от дорогостоящей сборки статической части.
- API Xray 26.3.27 поддерживает полную замену, append в конец и remove по тегу.
  Вставки по позиции, insert-before и replace-in-place нет. `lsrules` возвращает
  теги/выходы, а не полные уже собранные правила. В проверенном upstream main
  протокол по-прежнему не содержит позиции вставки.
- На отдельном временном процессе установленного Xray проверено: append с
  существующим ruleTag отклоняется; remove+append переносит динамическое правило
  после статических правил. Такой обход нарушает согласованный приоритет.
- Дополнительный воспроизведённый дефект старого Xray: полная замена очищает
  прежний набор до успешного построения всего нового набора. Синтетическая
  ошибка отсутствующего balancer оставила процесс живым, но прежний API route
  недоступным. Это отдельный серверный риск, не основание автоматически
  перезапускать рабочий Xray или менять его конфигурацию. В upstream main
  реализация уже собирает новый набор перед публикацией; это не означает,
  что исправление есть в установленной версии или проверенном release.
- Рассмотренный вариант оптимизации без изменения порядка: прямой gRPC и
  повторное использование подготовленной статической protobuf-конфигурации
  в памяти helper. Он устраняет повторное чтение .dat клиентским subprocess,
  но не полную замену/построение matchers на сервере. Сам по себе прямой gRPC
  без переиспользования статической части не устраняет сборку геобаз. Нужны
  дополнительные зависимости, корректное обновление при изменении config/assets,
  оценка памяти/размера RPC и изолированный замер; внедрение требует решения.
- Обновление только динамической группы через API с сохранением места
  требует соответствующего расширения API Xray. Не маскировать его отсутствие
  серией удалений/добавлений статического хвоста: она создаёт промежуточную
  рабочую конфигурацию с изменёнными правилами и усложняет обработку отказов.
- Уточнение: в новых Xray есть штатная горячая перезагрузка geodata
  (PR XTLS/Xray-core#5992, merged 25 апреля 2026; наличие проверено в v26.10.17).
  В установленной 26.3.27 этого модуля нет. `geodata.cron` запускает reload по
  расписанию; без `assets` перечитывает уже существующие файлы без скачивания.
  Это не watcher изменения файла и не подтверждённый ручной API reload.
  Обновляются matchers существующих правил, поэтому не требуется переставлять
  правила через adrules или перезапускать процесс. При этом registry reload
  пересобирает живые matchers, а не гарантированно только изменившийся файл.
  Перед усложнением helper собственным protobuf-кэшем исследовать этот штатный
  механизм для USERLIST и внешних баз: задержку применения, ошибки, DNS/routing
  и стоимость reload. Переход на него и обновление рабочего Xray не согласованы.
- Изолированная проверка 21 октября подтвердила файловую схему на Xray
  v26.10.17: постоянные routing rules с `ext:geosite_user.dat:USERLIST` и
  `ext:geoip_user.dat:USERLIST`, `geodata.cron = "* * * * *"`, без `assets`.
  Атомарная замена файлов обновляет маршруты после следующего cron tick,
  без adrules и restart. Реальные HTTP-запросы через отдельный proxy inbound
  подтвердили добавление/удаление доменов и IPv4, пустые категории и повторное
  заполнение; PID не менялся. Контрольные процессы v26.10.17 без cron и
  v26.3.27 продолжали использовать исходные списки. Скрипт, логи и result.json:
  `/home/suridler/builds/geodata-reload-probe/`. Все тестовые процессы завершены.
  Это подтверждает механизм, но не готовность helper к переходу: ещё не
  проверены DNS selection, стоимость reload на больших базах и обработка ошибок.
- Отдельно подтверждена точечная работа API v26.10.17: `adrules --append`
  сохраняет существующие объекты Rule/Condition, строит только переданные новые
  правила; `rmrules` фильтрует массив указателей без пересборки оставшихся
  Conditions. Массив правил копируется/просматривается за O(N), это не полная
  пересборка matchers. Изолированный тест выполнил 20 циклов добавления двух
  правил и удаления по тегам после удаления тестовых geosite/geoip из доступных
  Xray путей. Все реальные HTTP-проверки статических и динамических маршрутов
  прошли, порядок статических правил сохранён, процесс не перезапускался.
  Артефакты: `/home/suridler/builds/xray-append-remove-probe/`.
  Медиана CLI+RPC в малом тесте: append двух правил ~25 мс, remove одного ~18 мс;
  это не замер производительности на полном рабочем routing. Append остаётся
  добавлением в конец, а remove+append не становится общей атомарной операцией.

Рабочие службы, config, runtime rules и policy routing в этом исследовании
не изменялись; тесты использовали синтетический config и отдельный loopback port.

Обязательные сценарии приёмки:

1. Успех обоих процессов; неизменные файлы; ровно один или ноль restart.
2. Внешний geosite недоступен/неверная checksum, geoip успешен; обратная комбинация.
3. Ошибка сборки одного пользовательского файла; другой остаётся самостоятельным кандидатом.
4. Failed Xray test одного процесса; другой процесс всё равно выполняется, его
   успешные изменения сохраняются. Ошибочный набор не остаётся действующим.
5. Ошибка записи одного файла; другой применён; проверен именно оставшийся набор.
6. Failed restart: данные не откатываются, обновление файлов и критическая ошибка
   шлюза отображаются раздельно; ресурсы пользователя не теряются.
7. Ошибка восстановления динамических правил, завершения состояния или очистки:
   точный этап/причина в панели и журнале, без неверного сообщения о полном успехе.
8. Interrupted process/перезапуск helper: понятный незавершённый результат и
   сохранённые необходимые временные данные, без скрытого общего отката/reboot.
9. Отсутствующий раздел/отдельные ключи TOML, частичные настройки, явно заданные
   значения, ручное редактирование, сохранение из панели, конкурентное сохранение
   и ежедневный запуск/отключение: единые defaults, явные значения сохранены,
   нет зависимости от прежних настроек в БД.
10. Панель: штатная карточка без подробностей, красная ошибка со ссылкой,
    частичный успех в деталях, успешный повтор снимает текущую ошибку.

### N9 — независимый запуск TProxy: пересмотренный простой lifecycle

Пользователь пересмотрел решение 20 октября 2026 года. Выбираем **простейший
надёжный механизм**; дополнительная сложность допустима только при доказанной
необходимости и явном согласовании. Локальный кандидат `helper-v0.2.0-beta.4`
на commit `0eb9d59` отозван: его результаты не подтверждают новый вариант.
Упрощение реализовано; локальная регрессия пройдена. На тестовом WSL проверены установка, stop/start, restart без helper, reboot и crash;
LAN и failure injection add route/rule ещё не проверены. Подробности — в TESTING.

Согласованный контракт:

- Обычный постоянный nft-профиль, как до миграции (`bfd76d7`): без отдельных
  переключаемых цепочек, Python lifecycle, marker/lock, adopt/resume.
- Xray post-start всегда запускает routing unit строгим `systemctl start`;
  отдельного enable/автозапуска routing нет. Перед стартом, при штатной остановке
  и после завершения Xray hooks останавливают routing.
- Routing unit выполняет только native ip-команды: добавить local route, затем
  fwmark rule; при очистке удалить rule, затем точный local route. `ExecStopPost`
  обеспечивает очистку также после частичного failed start. Глобальной очистки
  таблиц и чужих маршрутов нет.
- Hooks находятся в `50-tproxy.conf`, основной unit Xray не переписывается.
  У routing нет `After`/`BindsTo` к Xray и нет `[Install]`; встречного ожидания нет.
  Drop-in задаёт `Wants`/`After` для штатных nftables/systemd-sysctl.
- Boot не зависит от helper CLI/daemon/TOML/SQLite/API. Helper не добавляет
  readiness gate; owner/group/mode внешних файлов не сканируются и не исправляются.
- Setup готовит файлы; единственный вспомогательный asset — Xray drop-in —
  устанавливается явным safe-apply TProxy-unit. Новый baseline: nft/sysctl/unit
  и drop-in (4 файла); исторические группы из 3 файлов восстанавливаются.
- Явный TProxy apply выполняет daemon-reload, helper sysctl oneshot, native nft
  load и restart Xray; routing запускает только строгий hook Xray. До перевода
  оператор выполняет `systemctl disable xray-tproxy-routing.service` без `--now`,
  удаляя прежний независимый автозапуск. Автомиграции symlinks нет.
- Обновление/удаление helper не подменяет действующую native-сеть. Четыре поставляемых рабочих
  шаблона обновляются вместе с helper; их применение к системе остаётся явным. Production в этой работе не трогаем.

Приёмка включает отсутствие helper, failed start/частичный route add, stop/crash,

и требует ручного reboot; текущие проксируемые соединения при stop не сохраняются.
Неоднозначные решения согласовываются до реализации. Статус новой регрессии
и серверной приёмки фиксируется в [TESTING](TESTING.md).

### D6. Единый ввод доменов и IPv4 в CLI/web

#### Границы и контракт

- На главной и в маршрутизации одно поле «Домен или IPv4» и действие «Добавить»;
  примеры `example.com` и `192.0.2.1`. Сохраняем существующую компоновку панели.
  Пользователь не выбирает тип вручную. IPv6, CIDR, URL и ошибочные IPv4
  отклоняет общий классификатор helper; web и CLI не создают своих валидаторов.
- Сохраняем команду `proxy-domain`, endpoint `/v1/proxy-domains`, поле `domain`
  и существующие JSON-поля списков. Они уже принимают оба типа. Не добавляем
  альтернативные команды, миграции БД, отдельное хранилище или импорт.
- В подписях, счётчиках и сообщениях используем «Домены и IPv4»/«Записи».

  динамическая, в основном списке, ожидает удаления. Источником остаётся helper.

  сохранение desired и применение в Xray. При возможном сохранении и сбое
  применения/получения свежего списка показываем неопределённость результата;
  не заявляем об откате или отсутствии записи и не повторяем мутацию автоматически.
  Это одинаково относится к добавлению и удалению.
- При недоступном helper, recovery, safe-apply и выключенном control действуют
  существующие ограничения. Потеря связи не превращает старые данные в свежие.
  Отсутствие настроенного proxy продолжает явно обозначать прямой выход.

### U6. Самообновление helper — перед обновлением панели

Backend/API/CLI и web-интерфейс реализованы локально (U6.1–U6.11); U6.12 ожидает двух release bundles и серверной приёмки.
Основа — публичный GitHub release с предсобранными
бинарниками, `release.json` schema1 и `SHA256SUMS`. Сборка Go на сервере не
требуется. Ниже — фактический контракт.

- Bootstrap тонкий: определяет Linux amd64/arm64, скачивает raw CLI выбранной
  версии и `SHA256SUMS` (четыре платформенных asset), проверяет SHA256 и
  запускает CLI. `gh`, токен, распаковка архива и Go не нужны; Node/npm нужны
  только для web-панели. Явная `--version` фиксирует точную версию, `--recover`
  работает офлайн от сохранённого root-private installer. API использует
  сохранённую проверенную копию текущего installer; bootstrap требует raw CLI
  целевой версии.
- `install` — самостоятельный режим без daemon: setup останавливает helper/web,
  берёт runtime lock и работает без socket. `update prepare` затем `apply`
  требуют operation ID и отдельный action ID; `retry`/`rollback` только явные,
  автоматического повтора/отката нет. Точная версия API может быть новее,
  старше или совпадать с установленной.
- `minimum_installable_version` — необязательное поле bundled `release.json`
  schema1. Без поля нижней границы нет; проверка идёт до замены файлов и без
  daemon, поэтому bootstrap её не обходит. Rollback возвращает согласованный
  снимок файлов/данных независимо от downgrade-policy.
- Журнал, installer, кандидат и снимок находятся в
  `/var/lib/xray-core-helper-update`, вне восстанавливаемых каталогов. После
  прерывания daemon обслуживает минимальный recovery API, обычные изменения
  блокируются. Обновление не перезапускает Xray/TProxy, не меняет сеть/config и
  не запускает setup. Сохраняются TOML/БД, backups, дополнительные пользовательские файлы, установленная
  панель и admin drop-in; заменяются поставляемые рабочие/заводские templates и managed files.

#### Согласованное поведение

- Обновлять весь установленный комплект одной версии: daemon/CLI, установленную
  web-панель, заводские шаблоны, принадлежащие установщику service-файлы и
  поставляемые зависимости. Отсутствующую панель не устанавливать.
- Сохранять настройки, БД, динамический список, backups и администраторские
  systemd drop-in. Четыре поставляемых рабочих шаблона обновлять вместе с helper;
  к системе их автоматически не применять.
  Не запускать setup, не менять Xray config/сеть и не перезапускать Xray/TProxy.
- Обновление запускает пользователь. Фонового применения новой версии нет.
- В web показывать установленную и последнюю доступную версии; кнопку «Обновить»
  показывать только при наличии более новой. При ошибке GitHub показывать ошибку
  проверки, а не утверждать, что обновлений нет.
- Учитывать стабильные и beta/prerelease-релизы helper, исключать draft.
  Выбирать максимальную SemVer, включая числовые части prerelease; даты публикации
  и лексикографическое сравнение не определяют новизну.

- Репозиторий релизов будет публичным: получать metadata и assets без токена,
  не переносить авторизацию пользователя из `gh`. Публикация репозитория здесь
  не выполняется; приватный доступ не входит в этот сценарий.
- API принимает явно выбранную версию, включая текущую и более старую, если
  установленная версия не запрещает такой downgrade. Это не отменяет проверку
  целостности, архитектуры и совместимости. Кнопка web предлагает новую версию.
- Установщик — самостоятельный режим существующего `xray-core-helper`, без
  обращения к daemon. Отдельный бинарник установщика не создаётся. Первичная
  установка, setup, обновление, повтор и откат используют этот режим.
- Bootstrap shell-скрипт только определяет платформу, скачивает соответствующий
  бинарник `xray-core-helper`, проверяет целостность и запускает его с переданными
  параметрами. Логики замены файлов, setup и восстановления в bootstrap нет.
- При запуске из API/web самостоятельный режим выполняется через `systemd-run`
  во временной службе, независимой от остановки daemon. Постоянный update unit и
  таймер не нужны. Запускается проверенная копия CLI из staging вне заменяемых
  каталогов, с фиксированным режимом и ID операции. Daemon не получает права
  записи в каталоги собственных бинарников. Вывод доступен через journal.

- Setup и применение обновления выполняются отдельным процессом при остановленной
  службе helper. Работающая служба может подготовить/инициировать обновление;
  перед записью состояния отдельный процесс останавливает её и исключает второго
  писателя. После выполнения запускает службу для проверки.
- После сбоя решение принимает пользователь: откат предыдущего комплекта с
  согласованными данными либо повторная установка выбранной новой версии.
  Автоматический откат и автоматический повтор не выполняются.

#### Восстановление после сбоя

До остановки helper сохранять operation ID, исходную/целевую версии и этап на
диск. Bootstrap, самостоятельный исполняемый установщик, проверенный bundle
кандидата и согласованную копию предыдущего комплекта/данных сохранять вне заменяемых каталогов, чтобы они были
доступны без работающих helper и панели. Повторная установка использует исходный
кандидат операции, а не незаметно выбирает более свежий release.

- Если helper запустился, он читает запись операции и проверяет, работает ли ещё
  процесс обновления. Незавершённая запись при работающем worker означает текущую
  операцию, при отсутствующем worker — прерывание. Записанный отказ показывается
  как ошибка. После сбоя API/CLI и доступная панель предлагают откат или повтор.
- Если helper не запускается, пользователь повторно запускает сохранённый
  bootstrap-скрипт, запускающий самостоятельный режим CLI под sudo. Исполняемый
  установщик читает запись и предлагает те же действия: откат либо повторную
  установку выбранной версии. Работающие daemon и HTTP API, а также установленная
  копия CLI не требуются: используется отдельно сохранённый/скачанный бинарник.
- Оба входа используют один сценарий восстановления и общую блокировку; перед
  изменениями служба helper останавливается. Откат возвращает комплект и
  согласованное состояние данных, а не только старый бинарник.
- При повторном запуске не перезаписывать исходную копию восстановления частично
  установленными файлами. Отсутствие или повреждение необходимых артефактов
  сообщать явно. Автоматического продолжения при загрузке сервера нет.

#### Согласованное ограничение downgrade

Поле `minimum_installable_version` реализовано в bundled metadata `release.json`
schema1 текущей установки и задаёт минимальную допустимую целевую версию. Без
поля разрешён выбор любой версии, прошедшей обычные проверки совместимости.
При несовместимой миграции release устанавливает нижнюю границу; проверка
выполняется до замены файлов и без обращения к daemon, чтобы повторный запуск
через bootstrap не обходил ограничение. Поле необязательное; по умолчанию
нижней границы нет.

Откат неудачной операции проверяется отдельно: возвращаются сохранённые данные и
предыдущий комплект как согласованная пара. Это не обычная установка старого
бинарника поверх новой БД и не подчиняется downgrade-policy. Неполный или
повреждённый снимок не применяется.

Запуск через `systemd-run` проверять с реальными ограничениями helper, включая
ожидание остановки и сохранность worker после замены установленной копии CLI.
Оставшиеся неоднозначные решения согласовывать при разработке соответствующего
контракта; перечисленные продуктовые решения повторного согласования не требуют.

#### Контроль результатов DeepSeek

- Каждая задача получает фиксированные интерфейсы, разрешённые файлы, критерии
  приёмки и зависимости. Агент не меняет lifecycle/политику восстановления сам.
- Первые параллельные задания после U6.1 — U6.2 и U6.3. U6.4 начинается после
  проверки их общего release-контракта. Код переносится только после ревью diff;
  рабочая копия пользователя не используется как площадка автономных изменений.
- Codex проверяет не только положительный путь: запускает негативные сценарии,
  проверяет отсутствие побочных записей, утечки секретов и скрытого расширения
  разрешений. Тесты DeepSeek оцениваются отдельно от написанного им кода.
- Codex самостоятельно выполняет относящиеся к задаче тесты. При завершении
  интеграции последовательно: `gofmt -d ./cmd ./internal`, `go test ./...`,
  `go test -race ./...`, `go build ./cmd/...`, `go vet ./...` из helper;
  `go test ./packaging`, syntax/fixture tests изменённых скриптов; `npm test`
  из web при изменениях панели. Документация — `git diff --check`.
- Приёмка узла замен/восстановления — отдельное ревью Codex до подключения API.
  Ни DeepSeek, ни локальные проверки не запускают реальные установки, службы,
  миграции или failure injection на текущем хосте.

Самостоятельный setup и install реализованы локально: lifecycle допускается
только при остановленной службе с общей блокировкой; setup не обращается к socket.
`AGENTS.md` и архитектурную документацию при переносе изменений нужно привести в
соответствие этому исключению из правила «только daemon пишет». Обычные команды
CLI остаются API-клиентами; универсальный offline-редактор или обход
mutation/recovery gate не добавляется.

#### Уточнения после независимого ревью DeepSeek

Codex проверил замечания DeepSeek Flash и включил в контракт следующие требования:

- Operation ID обозначает исходную операцию; явные apply/retry/rollback имеют
  отдельные ID попыток и ключи идемпотентности. Original candidate и original
  snapshot неизменны. Повтор запроса не равен новой попытке восстановления.
- Worker определяется по operation ID, boot ID и systemd InvocationID вместе
  с общей блокировкой. PID не является достаточным доказательством. Ошибка чтения
  systemd или противоречивые признаки дают неизвестное состояние и запрещают
  второго писателя; отсутствие ответа не трактуется как разрешение начать повтор.
  В U6.1 отдельно описать передачу владения от daemon к worker и окно до старта unit.
- Для существующих путей установки нужен журнал намерений и завершённых замен,
  сохранённый до соответствующих записей, атомарные rename и синхронизация на диск.
  После crash различать исходное, новое и смешанное содержимое; один общий флаг
  `applying` не доказывает целостность комплекта. Смена layout на versioned-каталоги
  не требуется этим планом.
- Запись операции и recovery-артефакты хранятся вне заменяемого дерева и вне
  снимка, который восстанавливается при rollback: откат данных не должен стирать
  собственный результат/блокировки. Состав снимка и согласованность SQLite/WAL
  явно определить до реализации, снимок делать после остановки всех писателей.
- Bootstrap использует фиксированную версию установщика для операции. При
  сохранённом проверенном установщике recovery не требует сети, GitHub или npm;
  повтор использует готовый кандидат. Если нужных артефактов нет, показывать
  конкретную ошибку, не выбирать latest и не собирать другой кандидат молча.
- Проверенную копию CLI для `systemd-run` и кандидат защитить от изменения между
  проверкой и использованием; перед запуском повторно проверить identity/digest.
  Новый CLI должен распознавать поддерживаемую версию operation manifest.
- Release публикуется после подготовки полного набора CLI assets, bundles,
  metadata и checksums. Перед первым обновлением существующей установки составить
  inventory только известных управляемых файлов; неизвестные файлы не присваивать
  установщику и не удалять. Отсутствующую metadata не заменять выдуманной версией.

DeepSeek дополнительно получает небольшие независимые задачи: таблицу переходов
операции/попыток, resolver identity worker на fake-данных и fault-injection fixtures
для частичной замены. Их интерфейсы определяет Codex в U6.1/U6.5; результаты
включаются только после собственного ревью и запуска тестов Codex.

#### Контракт и ход операции

1. **Проверка версии.** Helper возвращает установленную версию/commit, последнюю
   доступную, результат сравнения и причину ошибки. Для dev-сборки, которую нельзя
   однозначно сравнить с release, возвращать отдельное состояние; не угадывать
   новизну по commit или времени. Чтение версии ничего не устанавливает.
2. **Подготовка.** Выбранные release ID/tag/commit и архитектура фиксируются в
   операции. Архив и checksums загружаются в staging с ограничениями размера и
   времени. Проверяются безопасные пути архива, manifest, SHA256 и архитектура.
   Проверка выполняется доверенным установленным кодом до запуска кода кандидата.
   Версионирование manifest должно позволять обновить поставляемые зависимости,
   не привязывая все будущие releases к текущему PIN domain-list-community.
3. **Проверка окружения.** До остановки служб проверить место, обязательные файлы,
   Node/npm для установленной панели, совместимость настроек и схемы БД. Пока
   сохраняется текущий формат bundle: web-зависимости готовятся через `npm ci`
   в staging, до замены. Автоматически устанавливать Node/Go не требуется.
4. **Явное применение.** Клиент подтверждает ID подготовленной операции и её
   версию. Появление нового release не меняет уже подготовленный кандидат.
   Перед заменой повторно проверяются конфликтующие операции и drift установки.
   Недостаточно проверить блокировки только в момент начала загрузки.
5. **Замена.** Запустить самостоятельный режим проверенной копии CLI через
   `systemd-run` во временной службе; установщик должен остановить helper с его внутренними
   задачами и установленную панель, получить согласованный снимок файлов и БД,
   заменить комплект и запустить новую версию. Запись/миграция БД не может идти
   одновременно со снимком. Новая служба не запускает фоновые мутации до разрешения
   состояния незавершённого обновления.
6. **Проверка результата.** Сверить версию/commit, доступность API helper и HTTP `/`
   установленной панели. Отдельно учитывать проблемы, существовавшие до обновления:
   например, прежняя ошибка геобаз не должна сама объявлять замену неуспешной.
   Успех/ошибка/результат восстановления сохраняются для CLI и web после restart.

Реализованные API/CLI: `check`, `prepare`, `apply`, `status`, `retry`,
`rollback`. Точные контракты — в [API](../xray-core-helper/docs/API.md).
Состояния: `preparing`, `prepared`, `launching`, `applying`, `verifying`,
`succeeded`, `failed`, `interrupted`, `rolled_back`; явные действия
восстановления — повтор установки и откат, с собственным сохранённым результатом.
Результат содержит operation ID, исходную/целевую версии, этап и код ошибки без
токенов и секретных заголовков. Повторный запрос с тем же ID читает существующую
операцию; потеря HTTP-ответа не разрешает повторную замену.

`install-bundle.sh --prebuilt` теперь передаёт управление
`bin/xray-core-helper install --bundle ROOT`: состояние операции сохраняется,
setup на чистой установке выполняется самостоятельно до запуска daemon, а при
обновлении не повторяется. Web-зависимости готовятся в staging (ручной
`npm ci` не нужен, но Node/npm должны быть установлены). Исходная shell-сборка
остаётся инструментом разработки и не является U6 updater. Каталог web заменяется
целиком, чтобы удалённые в release файлы не оставались; пользовательские данные
не находятся в заменяемом дереве. Заводские templates заменяются, рабочие
templates/TOML/БД и admin drop-in сохраняются.

#### Проверки перед релизом

Локальные unit/lifecycle/fixture-тесты реализованы; перечисленные ниже серверные
проверки, включая два release bundles, не заменяются ими и относятся к U6.12.

- Unit/contract: SemVer, stable/prerelease/draft, pagination, ошибки API/rate limit,
  отсутствие подходящего asset, неверные manifest/hash/arch и прерванная загрузка.
  Отдельно проверить выбор текущей/старой версии и запрет downgrade текущим release.
- Lifecycle: конфликт мутаций, повтор apply, drift после prepare, остановка на каждом
  этапе замены, отказ запуска новой версии, повторный запуск процесса обновления.
  Проверить оба ручных действия — повтор и откат комплекта вместе с данными —
  через API и через bootstrap/самостоятельный режим CLI при недоступном daemon.
  Проверить, что повторный запуск не затирает первоначальную копию восстановления.
- Packaging: с web и без неё; произвольные сохранённые настройки и working templates;
  отсутствие Go на сервере; недоступность npm выявляется до остановки панели.
- T8 на тестовом сервере: предыдущий release → новый release, сохранность desired/
  baseline и metadata файлов, отсутствие restart Xray/TProxy и изменений сети,
  работа helper/web после обновления и доступная диагностика отказа. Отдельно
  проверить восстановление после прерывания, включая перезагрузку хоста.

Изменение этого плана не запускает обновление текущего хоста. Серверную приёмку
самообновления проводить после локальной регрессии и сборки двух release bundles.

## 1. Установка и следующий релиз

- Проверить на сервере согласованный Xray-шаблон
  [`config.json`](../xray-core-helper/templConf/xray/config.json).
  Согласованные решения и критерии интеграции собраны в
  [каталоге шаблонов](../xray-core-helper/templConf/README.md#routing-and-dns-policy).
  Включён в установку в S7. Согласованы `AsIs`, direct по умолчанию,
  начальный proxy/freedom без секретов, разделение DNS, приоритет пользовательского
  списка после системных правил, logging defaults и отказ от webhook.
  Категории Cloudflare совпадают с `proxy-domain-ru-blocked`; постоянный USERLIST
  связан в DNS и routing одним значением. Динамические добавления/исключения
  до консолидации не синхронизируют DNS; это ограничение явно сохраняется.
  Индивидуальные домены пока остаются в шаблоне: после релиза перенести в USERLIST,
  проверить работу исключений и только затем удалить временное правило.
  Индивидуальные IP сохранить; разовый импорт прежних списков не добавлять.

- Проверить на сервере подготовку двух USERLIST assets нового шаблона.
  Подключение Xray renderer к setup реализовано локально: выбранная сеть, настройки
  helper, существующие порт/марка, повторная подготовка и блокировка drift. Типизированный
  renderer, `[logging]`, `geodata.user_geoip`, explicit template apply,
  сравнение/валидация и проверка backup реализованы локально. Рабочие копии setup,
  включая Xray, сохраняют содержимое и метаданные. Оба USERLIST asset и
  транзакционное logging API реализованы; основной шаблон включён в установку в S7.
  Все шаблоны,
  включая Xray working copy, остаются неизменными; prepare/apply создаёт отдельные
  кандидаты. Проверять значения helper против фактических значений системы без
  автоматического принятия drift. При подготовке существующей установки сохранять
  реальный proxy и неизвестные настройки; freedom — стартовое поведение.
  Native-часть реализована локально, требует серверной приёмки.

- Проверить на сервере `${user_geoip_reference}` в setup для `proxy-ip-permanent`: имя файла из helper,
  default `geoip_user.dat`, provider `helper.user-geoip`, тип `geoip-reference`.
  Разметка, типизированная подстановка и уникальный ID реализованы. Категория согласована:
  `USERLIST`, полная ссылка `ext:geoip_user.dat:USERLIST` при стандартном имени.
  Реализован единый механизм добавления ресурсов, различающий домен и IPv4;
  домены направлять в пользовательский geosite, адреса — в пользовательский geoip.
  Сохранить desired/baseline, добавления/исключения, консолидацию и восстановление
  runtime после перезапуска для обоих типов; IP-правила используют `ip`, не `domain`.
  Отдельный несвязанный IP workflow и импорт прежних списков не добавлять.
  До проверки Xray обеспечить валидный asset, включая пустую USERLIST на чистой
  установке, если Xray допускает её. Не подменять пустой список фиктивным IP.
  Проверить binding, сравнение, отсутствующий файл/категорию и восстановление.
  IPv6/CIDR не входят в это решение и требуют уточнения перед расширением.

- Завершить подключение настроек logging helper и bindings к setup:
  `access = "none"`, `error = ""` (stdout/journal), `loglevel = "warning"`,
  `dnsLog = false`. Пустой access означает stdout, а не отключение. Создавать
  файлы/права только при файловом назначении; сохранить сбор ошибок из journal
  и согласовать typed logging edits с настройками, чтобы apply их не затирал.
  TOML defaults/валидация, scalar renderer и транзакционное согласование
  реализованы локально; остаётся серверная приёмка.
  Для каталога журналов вне разрешённой области службы сначала показывать
  предупреждение; сохранение выбранной настройки требует явного подтверждения
  пользователя. Без подтверждения не менять настройку и ограничения systemd.
  После подтверждения сохранять и применять выбранную конфигурацию без
  автоматического расширения доступа systemd. Если Xray не запустился,
  показать ошибку и оставить сохранённую настройку для ручного исправления.
  Валидация проверяет настоящий кандидат; не подменять пути и не выполнять
  неоговорённые исправления. Проверка ограничений — предупреждение, а не
  доказательство доступности всех путей в реальной системе.


- Принять подготовку native-шаблонов с placeholders на тестовом сервере:

  она не заменяет серверную приёмку.

- Выпустить bundle с исправлениями working metadata и completedGeneration.
- Включить предсобранный закреплённый `domain-list-community` для обеих архитектур,

  Проверить добавление/удаление доменов и последующее обновление геобаз.

  USERLIST без фиктивного IP, private validation projection и восстановление

## 2. Проверка сети в setup — реализация и приёмка

Реализована проверка IPv4 DNS/шлюза/HTTPS до и после включения TProxy;
приёмка установленного bundle остаётся отдельным шагом.
Согласованный контракт:

- URL в настройках helper, по умолчанию `https://www.google.com/generate_204`,
  ожидаемый HTTP 204; ограниченный общий таймаут, без HTTP proxy из environment.
- Ping реального шлюза — дополнительный признак: его отказ не отменяет успех HTTPS.
- Показать дату/время, HTTP-код, результат и длительность до/после включения.
- HTTPS проверяет обычный исходящий путь сервера; LAN forwarding не утверждается.
- Сохранять результаты в helper с ID pending-транзакции после включения;
  решение пользователя хранить штатным safe-apply журналом.
- Всегда оставлять повтор проверки, confirm даже при неуспехе, rollback и ожидание
  таймера. Автоматического confirm и повторного apply после потери ответа нет.

Оставшаяся приёмка: новый bundle на тестовом сервере, успешная/неуспешная
HTTPS-проверка, ручное подтверждение при неуспехе и восстановление по timeout.

## 3. Операторская приёмка панели

Согласованный интерфейс (сохранить при дальнейших доработках):

- Ориентир — пошаговая установка и главная панель 3x-ui; светлая тема,
  боковая навигация и понятные подписи во всех разделах.
- В верхнем ряду «Общее состояние шлюза» и «Динамический список» занимают
  по половине рабочей зоны; на узком экране идут друг под другом.
- Общее состояние охватывает helper, Xray, сеть и конфигурацию. Здесь же
  дата/время обновления геобаз и действия «Обновить геобазы» / «Настроить».
- Добавление домена в динамический proxy-список доступно сразу на главной.
- Ниже остаются два графика: приём и передача Xray, пока источник — exporter.
  Четыре отдельные карточки состояния не возвращать.
- Один блок «Журнал Xray»: по умолчанию последние ошибки, переключение
  на все события/предупреждения/информацию; текущий журнал обновляется периодически.
- Helper хранит последние 100 отдельных ошибок без срока давности и агрегации;
  одинаковые записи остаются отдельными, с собственным временем; на главной — 5.
- При недоступности helper не показывать сохранённое состояние как актуальное.
  Confirm/rollback и предупреждения recovery доступны во всех разделах.

Эта компоновка реализована в `e4c9956`; дальнейшая работа — реальная приёмка
и исправления по её результатам, без повторного изменения согласованной структуры.

Светлая компоновка с боковым меню, общая сводка, графики, динамические домены,
события и постоянные ошибки реализованы. Проверить установленный bundle
в браузере оператора: понятность подписей, фактические данные exporter,
потеря связи и подтверждение сетевых настроек во всех разделах.

Критерий: навигация и действия понятны на desktop/mobile; предупреждения
recovery и таймер подтверждения доступны независимо от выбранного раздела.

## 4. Приёмка и безопасность

Внутренний планировщик реализован: errors каждые 20 с, reconcile каждые 30 с,
геобазы ежесуточно по `[scheduler]` (по умолчанию 04:00, можно отключить).
Rollback остаётся в systemd. Проверить обновление существующей установки,
отключение старых таймеров, пропущенный ежедневный запуск и отсутствие спама
в журнале по сценарию [TESTING](TESTING.md).


Проверить на установленном bundle сбор ошибок внутренним планировщиком, сохранение истории
после reboot и графики с работающим exporter. Завершить остальные отдельные
сценарии из [TESTING](TESTING.md), затем:

- Проверка Unix peer credentials и раздельные read/mutate permissions.
- Browser origin/host, sessions/CSRF.
- Audit с проверенным actor без bodies/secrets.
- Повтор CLI/web/scheduler/exporter под окончательной политикой доступа.

Критерий: разрешённые клиенты работают с минимальными правами; отклонённые
запросы не меняют state, отказ control plane не ломает routing.

### CLI safe-apply: подтверждение и явное восстановление

Реализованы подтверждение в одной команде с обратным отсчётом и запросом статуса
каждые 5 секунд; `templates apply ... -force` без таймера;
`safe-apply cancel-reboot ID` и самостоятельный `--offline` для остановленного
helper. Отмена сохраняет историю и не меняет runtime. Локальные проверки и
операторская проверка на сервере фиксируются отдельно в TESTING.md.

#### Открытый дефект: повтор проверки из CLI

При операторском применении TProxy-unit 20.10.2026 пункт `3` визуально был
введён, но CLI ответил «Введите номер одного из вариантов»; повторная сетевая
проверка не выполнялась. Последующее подтверждение прошло, HTTPS после него — 204.
Локальный тест точного ввода `3\n1\n` проходит и проверяет два запроса probe
при единственном apply. Причина расхождения не установлена: требуется проверить
реальный терминальный ввод и перерисовку countdown. Не считать дефект закрытым
по одному unit-тесту; при приёмке проверить ввод `3` во время обновления счётчика.

Перерисовка countdown исправлена: строка ввода больше не переписывается.
В PTY успешно проверен набор `33`, обновление countdown, Backspace до `3`,
Enter, повтор probe и подтверждение: один apply, два probe. Это регрессия для
терминального сценария; точный состав исходного отклонённого ответа неизвестен,
поэтому операторскую проверку первоначального дефекта пока не считаем закрытой.
