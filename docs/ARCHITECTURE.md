# Архитектура

Документ описывает реализованную beta. Будущие возможности перечислены
отдельно в [плане развития](ROADMAP.md).

## Компоненты и источники истины

```text
Браузер -> xrayui-web -> Unix socket -> xray-core-helperd
CLI -------------------- Unix socket -------^
                                             |-> Xray JSONC и geodata
                                             |-> RoutingService
                                             |-> фиксированные systemd-операции
                                             `-> транзакции и восстановление

Xray Routing Webhook -> xray-routing-exporter -> SQLite / JSON API / Prometheus
Xray StatsService ---> xray-routing-exporter

Xray + nftables + policy routing -> обработка трафика
```

| Состояние | Источник / владелец |
| --- | --- |
| Xray settings | Один JSONC-файл, выбранный effective xray.service |
| Изменения config, proxy domains, geodata | Helper |
| Системные правила и их семантика | Нативные nftables/sysctl/systemd-файлы |
| Настройки web | [web] в Helper TOML |
| Routing events и счётчики трафика | Exporter |
| Жизненный цикл и аварийный rollback | systemd |
| Периодические задачи обслуживания | Внутренний планировщик helper |

Helper SQLite хранит generations, hashes, desired/baseline доменов и evidence
транзакций, а не вторую полную модель Xray config. Web/exporter получают
типизированные проекции, не читают и не меняют config напрямую.

## Самостоятельная установка и обновление

Обычные команды CLI остаются клиентами API. `install`, изменяющий `setup` и
восстановление установки используют те же внутренние сервисы без daemon и
без socket/listener. Перед записью остановлены helper/web и удерживается общий
`runtime.lock`; перед запуском daemon блокировка освобождается. `setup --status`
остаётся чтением API. Веб-панель направляет первичную настройку в консоль.

API обновления запускает сохранённый installer через разовый `systemd-run`.
Проверка/скачивание кандидата предшествуют остановке служб. Журнал операции,
кандидат и полная копия файлов/данных находятся в закрытом
`/var/lib/xray-core-helper-update`, отдельно от восстанавливаемого состояния.
Откат проверяет всю копию до первой записи. Незавершённая установка блокирует
обычные изменения; daemon при возможности запускает ограниченный recovery API.
Повтор и откат выполняются только по команде пользователя, включая случай,
когда требуется запустить сохранённый bootstrap без daemon. Обновление не
перезапускает Xray/TProxy и не повторяет setup. Точный API и границы совместимости
описаны в [API](../xray-core-helper/docs/API.md).

## Пути и setup

Executable, один config и assets обнаруживаются по effective `xray.service`.
Требуется direct ExecStart с одним абсолютным `-config`/`-c` и явным
`XRAY_LOCATION_ASSET`. Wrapper, confdir и неоднозначные пути
отклоняются. `/usr/local/etc/xray/config.json` — стандартный пример,
а не самостоятельная настройка Helper.

`discover-xray` работает до запуска daemon. Установщик создаёт собственный
systemd drop-in с разрешениями для обнаруженных путей. HTTP API не принимает
произвольные пути и не расширяет confinement по запросу клиента.

Настройка logging сохраняет `[logging]` TOML вместе с typed JSONC edits;
renderer получает текущие значения для последующих apply. Приватный журнал
связывает снимки TOML с generation/hash Xray и восстанавливается после основной
конфигурационной транзакции. Файловые журналы подготавливаются под effective
UID/GID службы Xray; существующим родительским каталогам права не расширяются.
Каталоги вне разрешений systemd требуют предупреждения и явного согласия.
После согласия ограничения службы остаются прежними, а отказ запрошенного
restart оставляет настройку сохранённой для ручного исправления. Кандидат при
валидации не подменяется; остальные отказы сохраняют обычную семантику отката.

Наличие config не завершает setup: завершение хранится в versioned helper
operation, привязанной к config target. Существующий Xray можно явно принять
без изменения сети либо подготовить для TProxy. При создании используется
заводской Xray-шаблон. Pending recovery имеет приоритет над setup.

Согласованные нестандартные port/egress mark сохраняются. Недостающие поля
добавляются узкими JSONC edits; неоднозначность требует разбора либо явно
подтверждённой замены. Подготовка файлов и активация TProxy — разные шаги.

## Профиль сети

Заводской профиль перехватывает публичный IPv4 TCP/UDP выбранного LAN-интерфейса
и самого сервера через OUTPUT/loopback. Local/reserved destinations, исходящая
марка и socket GID Xray обходят перехват. `proxy_clients` сам по себе
не ограничивает клиентов. ICMP и IPv6 не проверяют этот TProxy-путь.

Заводские значения: TProxy port `52345`, interception mark `1`, egress mark
`255`, policy table `100`. Общий движок Helper не навязывает числа, имена
таблиц/цепочек или обязательные sysctl keys: семантика принадлежит шаблону.

Постоянный nft-профиль содержит обычные правила TProxy и OUTPUT marking.
Lifecycle не переключает цепочки nftables: направление маркированных пакетов
в локальный Xray включается policy routing. Штатные nftables и systemd-sysctl
загружаются через `Wants`/`After` в отдельном
`/etc/systemd/system/xray.service.d/50-tproxy.conf`; основной unit Xray не меняется.

Строгий `ExecStartPost` Xray всегда запускает `xray-tproxy-routing.service`.
Она добавляет local route, затем fwmark rule. Перед стартом Xray, при штатной
остановке и после завершения hooks останавливают routing unit. Её `ExecStopPost`
удаляет rule, затем точный local route, в том числе после failed start.
Встречных `After`/`BindsTo` к Xray и собственного `[Install]` у routing нет;
отдельного enable нет. Ошибка активации делает запуск Xray неуспешным.

В boot-пути используются только systemd и native ip-команды. Нет Python
lifecycle, marker/lock, adopt/resume, вызовов helper/TOML/SQLite/socket/API.
Forwarding, sysctl, постоянные nft-правила и чужие маршруты при остановке Xray
не меняются. Снятие policy rule возвращает маркированный OUTPUT в main routing.
Здесь fail-open означает снятие policy route/rule, а не удаление nft-перехвата
или гарантию работы всей сети без Xray; текущие соединения и DNS зависят от
фактической конфигурации.

Setup готовит native-файлы. Единственный вспомогательный asset, Xray drop-in,
устанавливается при явном safe-apply TProxy-unit; обновление factory-источника
не подменяет действующий drop-in. Удаление helper сохраняет native-сеть.
Перед заменой routing unit старая служба останавливается с прежними параметрами.
Явный apply после установки drop-in выполняет daemon-reload, применяет sysctl
через helper oneshot, загружает управляемый nft-блок native adapter и перезапускает
Xray. Его строгий post-start запускает routing. Отдельной проверки is-active
с последующим независимым запуском routing нет. Эти операции helper не входят
в boot path. Привилегированная приёмка новой схемы на сервере остаётся отдельным этапом.

Явный `network-check` — однократная диагностика service/config/bindings/socket/API
с безопасным кодом этапа ошибки. Он не участвует в запуске служб и не
доказывает LAN forwarding. Owner/group/mode существующих системных файлов не
являются критерием исправности; реальные I/O errors и ошибки конфигурации остаются.

До/после включения TProxy CLI/web вызывают типизированный network probe helper:
IPv4 DNS, маршрут к проверенному адресу, ping шлюза и HTTPS с ожидаемым кодом.
Трафик не получает обходных socket marks и не использует HTTP proxy environment.
Ping — дополнительный признак, HTTPS не доказывает LAN forwarding. Helper хранит
последние before/after/latest в приватном `network-probes.json` рядом с SQLite;
after содержит ID safe-apply, решение оператора остаётся в её штатном журнале.
Настройки `[connectivity]` изменяются через helper settings. Проверка доступна
при pending и не блокирует право оператора подтвердить неуспешную конфигурацию.


## Транзакции и шаблоны

Xray config меняется структурированно: generation/hash check, узкие edits,
native validation, backup, атомарная замена, явно запрошенный или необходимый
restart и восстановление при ошибке. Comments/unknown fields сохраняются.
Внешнее изменение config блокирует запись до validate/adopt.

Для nftables/sysctl/systemd используются фиксированный каталог, native validators
и доверенные adapters. Подстановки и проверки связей разрешены только явными
annotations. nft меняется внутри `helper:begin/end gateway`; внешний текст
сохраняется. Первичная разметка существующего файла требует preview и confirm.
Синтаксическая проверка не доказывает совместимость с чужими правилами.

Поставляемые рабочие шаблоны обновляются вместе с helper; системные файлы
не заменяются автоматически. Пользователь решает, применить новую схему или
принять действующий системный вариант. Откат обновления возвращает прежние шаблоны.
Миграция сохранённых параметров между версиями — отдельная задача.

Перед системным apply фиксируется единый baseline из четырёх файлов:
nft/sysctl/routing unit и Xray drop-in.
Rollback, timeout или прерванный неподтверждённый apply восстанавливают всю группу,
её UID/GID/mode и исходное отсутствие. Историческая группа из трёх файлов
поддерживается только для восстановления ранее записанной операции. Live-эффекты не откатываются:
после полного восстановления нужен ручной reboot.

Частичный restore блокирует записи. Полный restore сохраняет `awaiting_reboot`;
завершение требует нового kernel boot ID и совпадения baseline. Рестарт
Helper/web не заменяет reboot. Pending evidence защищено от retention.
Гарантия не охватывает необратимые внешние эффекты произвольных unit commands.

Подробности: [контракт нативных шаблонов](../xray-core-helper/docs/NATIVE_TEMPLATES.md).

## Динамические домены и geodata

`desired - baseline` формирует runtime proxy additions, `baseline - desired` —
direct exclusions. Overlay применяется через RoutingService без рестарта.
При сбое runtime desired может уже сохраниться; повторный apply согласует его.
Точка вставки — постоянное правило `proxy-domains-permanent`. Порядок:
системные правила, dynamic direct exclusions, dynamic proxy additions,
пользовательский geosite, остальные пользовательские правила. Динамические
правила формируются в runtime; пустые заглушки в конфиге не нужны.
Внутренний планировщик helper раз в 30 секунд запускает `proxy-domain reconcile` через тот же Unix API.
Helper сравнивает systemd InvocationID и восстанавливает runtime overlay только
для нового запуска Xray / первого вызова после запуска helper. Успех фиксируется
в памяти после apply и повторной проверки InvocationID; ошибка повторяется на
следующем тике. Остановленный Xray планировщик не запускает; это не синхронный hook запуска Xray.
Замена файлов и runtime apply сериализуются общим координатором. Скачивание
внешних файлов выполняется до его захвата.

На главной web-панели и в маршрутизации доступно добавление домена без рестарта.
При ошибке синхронизации desired может уже сохраниться: панель обновляет список
чтением, сохраняет предупреждение и введённый домен, не повторяя POST.
Начальный proxy-as-direct явно обозначается; это не запрещает добавление доменов.

Настройки геобаз принадлежат только TOML helper. Отсутствующие ключи получают
встроенные defaults: runetfreedom geosite/geoip и SHA256, разрешённый origin
raw.githubusercontent.com, лимит 256 МБ, ежедневный запуск 04:00. Явные значения,
включая пустой список origins, сохраняются. Старая конфигурация в БД не читается
и не переносится. API/панель сохраняют TOML с проверкой generation снимка;
каждая операция получает один снимок. Ручная правка действует без restart helper.

Один цикл последовательно выполняет два независимых процесса: скачивание
внешних баз и сборку USERLIST из desired. У внешнего файла обязательна своя
SHA256; отказ одного файла не отменяет допустимый результат другого. У каждого
процесса свой общий `xray run -test` для подготовленных кандидатов и остальных
действующих файлов. Замена — временный файл и atomic rename. При частичной ошибке
записи повторно проверяется фактическая смесь; только failed test восстанавливает
заменённые файлы этого процесса. Другой процесс не откатывается.

Один restart Xray в конце выполняется при фактических заменах или завершении
прерванной активации ранее заменённых файлов. Хеши перед rename сохраняются
в SQLite: неудачная запись либо восстановленный файл не требуют лишнего restart. Неуспех
restart — критическая ошибка шлюза, отдельно от результата файлов, без их отката.
До rename сохраняются hash и прежний runtime, для пользовательского файла —
также собранные ресурсы. Эти записи позволяют повторить прерванную активацию
без повторной замены совпадающих файлов.
Новый baseline активируется только для совпавшего файла после нового запуска Xray;
затем применяется overlay. Отказ активации повторяется штатным routing reconciler,
desired не теряется. Отдельной длительной блокировки пользовательского списка нет.

SQLite хранит результаты операций и историю ошибок, а не настройки. При запуске
helper прерванная running-операция становится failed с `geodata_interrupted` и
последним этапом. Автоматического общего rollback/reboot нет. Временные предыдущие
файлы сохраняются до завершения процесса; при неудаче восстановления evidence
остаётся для оператора. Очистка после успешного применения даёт предупреждение.
На главной панели — дата выполнения и следующего запуска; ошибки раскрываются
с этапом, причиной, временем, ID операции и командой поиска записи в journal.

Пользовательский geosite управляется по имени `[geodata].user_geosite` из
`config.toml`, по умолчанию `geosite_user.dat`. Консолидация и Xray validation
используют одно имя. Явная аннотация
`source=helper.user-geosite type=geosite-reference` связывает имя в Xray с настройкой
при подготовке/apply; категория сохраняется, непомеченные ссылки не меняются.
После смены настройки пользователь сам переименовывает файл. Другие файлы автоматически
не переносятся и не удаляются. При подготовке сети setup создаёт отсутствующий
пользовательский geosite с техническим `.invalid` доменом в USERLIST, проверяет Xray
на временных assets и включает файл в durable recovery. Существующий файл
сохраняется; общий редактор не удаляет постоянное правило. Если кандидат Xray
содержит ссылку на настроенный `[geodata].user_geoip` (по умолчанию
`geoip_user.dat`), setup подготавливает отсутствующую пустую USERLIST без
фиктивных IP и восстанавливает оба assets вместе с конфигом/TOML.

Консолидация создаёт пару пользовательских geosite/geoip из одного замороженного
снимка. В geosite передаются только домены, в geoip — IPv4 `/32`. Оба кандидата
и их hashes проверяются до замены первого файла; Xray проверяет временную
проекцию assets. Один manifest v3 хранит обе предыдущие версии и metadata.
Baseline фиксируется одной транзакцией после проверки обоих live-файлов и
согласования runtime. После сбоя между заменами recovery распознаёт смешанную
пару и восстанавливает её; неизвестный drift блокирует запись. Сбой cleanup
после commit допускает повторную очистку, без отката baseline.
Это реализованный внутренний lifecycle; подключение смешанного списка к
runtime/CLI/web и включение нового установочного Xray-шаблона остаются в
[плане](ROADMAP.md). Старые pending manifest не преобразуются автоматически:
нераспознанные evidence сохраняются и блокируют изменения для ручного разбора.

## Web и безопасность beta

Daemon работает как root и слушает только Unix socket, по умолчанию
`root:xray-core-helper 0660`. Текущая модель доверия основана на правах сокета;
детальная peer-авторизация и audit ещё не реализованы.

Web работает как `xrayui-web` с группой `xray-core-helper`. Перед bind получает
настройки Helper. Runtime web.env содержит socket и временный setup token,
но не listener/control settings. После запуска API Helper просит systemd
запустить статический web unit. Headless не требует Node или web account.

Остановка Helper/web/exporter не выключает data plane. Уже работающая web-панель
при недоступном Helper показывает ошибку. HTTP-аутентификация и полная защита
browser mutations пока отсутствуют: beta остаётся на loopback с туннелем.

Только выделенный sysctl oneshot получает `ReadWritePaths=/proc/sys`.
Daemon сохраняет `ProtectKernelTunables=true`. Executable/config oneshot
фиксированы; annotations и HTTP не задают команды.

## Телеметрия и диагностика

Exporter поддерживает приём webhook и независимо опрашивает StatsService.
В текущем установочном Xray-шаблоне webhook выключен; графики используют StatsService. API address/tags
получает от Helper, сохраняя последний допустимый snapshot при его недоступности.

Webhook фиксирует выбор маршрута, а не успешность соединения; events не равны
байтам или HTTP-запросам. Два графика web используют разность накопительных
байтовых счётчиков только outbound из `/api/v1/xray/stats`: downlink — приём,
uplink — передача. Inbound не суммируется повторно. Это трафик Xray, а не всей
сетевой карты. Источник задаётся `[web].exporter_url` Helper; разрешён HTTP
origin на числовом loopback, пустое значение отключает чтение. Timeout — 2 с,
ответ ограничен 256 KiB, redirect запрещён. До двух свежих snapshot, при сбросе,
смене набора счётчиков или устаревании более 45 с скорость недоступна, а не ноль.
Единый блок «Журнал Xray» на главной по умолчанию показывает сохранённые ошибки.
В режимах «Все события», «Предупреждения» и «Информация» записи читаются из error-журнала Xray
(последние 100 строк, показываются восемь новых строк выбранного уровня).
Обновление раз в десять секунд работает на видимой главной вне setup только
при выбранном режиме событий; при сбое
предыдущие события сохраняются и помечаются устаревшими. Это окно текущего
журнала, а не постоянная история ошибок; дополнительный info logging не включается.
Helper отдельно хранит в своей SQLite последние 100 отдельных ошибок без
агрегации и удаления по возрасту. На главной показываются пять: повторяющийся
текст с разными исходными позициями/курсорами остаётся разными событиями.
Исходное время и время получения сохраняются отдельно; неизвестное время
ошибки не подменяется временем получения. Секретные URI/записи скрываются до
сохранения. Checkpoint предотвращает повторную вставку при перечитывании.
Сбор запускает внутренний планировщик helper каждые 20 с.
Задачи работают независимо, без наложения запусков одной задачи и без сообщений
об успешных тиках. Ошибка и восстановление журналируются только при смене состояния.
Планировщик работает только после завершения setup и отменяет задачи при остановке.
Запросы идут через тот же Unix API с проверкой путей Xray, safe-apply и recovery gates.
Ежедневное обновление геобаз включено по умолчанию в 04:00 по времени сервера;
`[scheduler].geodata_update_enabled` и `geodata_update_time` меняются в TOML или панели; планировщик перечитывает их раз в минуту без restart helper.
Первый запуск назначается на ближайшее будущее время; сохранённый пропущенный
запуск выполняется один раз после старта. SQLite хранит дедлайн, API — ключ
идемпотентности запуска. Таймер аварийного отката остаётся в systemd.
Источник — настроенный error-файл либо journald Xray; info logging не включается.
Читается ограниченное окно: до 1 MiB/10000 строк файла или 200 ошибок journal.
После первого сбора journal ограничен временем предыдущего успешного прохода.
Пропущенное вне окна/во время остановки источника не гарантируется восстановить;
успешно сохранённые ошибки остаются до вытеснения новыми. Статус API отражает
сбой сбора, отключённый источник и ограничение окна отдельно от самих записей.
Общая сводка панели объединяет Helper, Xray, конфигурацию, локальные сетевые
проверки, TProxy и readiness. Выключенные TProxy/автообновления отображаются
отдельно от ошибок; доступ в интернет явно не проверен. Старые сообщения журнала
не превращаются в неисправность текущего состояния. Web больше не ведёт отдельный
процессный счётчик критических ошибок и не опрашивает для него журнал в фоне.
При частичной недоступности диагностики сводка показывает неизвестное состояние;
при сбое обновления сохраняет последний snapshot как устаревший и блокирует
изменения. Pending safe-apply и reboot/recovery видны во всех разделах, неизвестное
состояние safe-apply блокирует записи. Обновление шаблонов не снимает блокировку
другой операции. Вкладки настроек имеют адреса `#settings/system` и `#settings/logs`.
Автоматическая проверка интернета в setup остаётся в roadmap.
